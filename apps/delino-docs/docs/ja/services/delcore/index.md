# Delcore

Delcore は、Delino サービス向けに共通のテナント、アクセス制御、請求機能を提供します。公式 API サーバーは `https://delcore.api.delino.io` です。このページでは、サービス開発者向けに、従量料金、レコードの有効期限、テナント状態の確認について説明します。

## テナント状態の確認

登録済みのサービスは、テナントが有効、ブロック済み、削除済みのいずれであるかを Delcore に問い合わせることができます。サービスがテナントのデータを保存しているものの、リクエストごとに Delino ユーザーが存在するわけではない場合、たとえばプロジェクト API キーで呼び出しを行う場合に、この確認を使用してください。

1〜100 個のテナント ID を指定して `delcore.v1.DelcoreService/GetTenantStates` を呼び出します。各 ID は小文字の UUID バージョン 7 である必要があります。サービスの Logto マシン間アプリケーションのアクセストークンで認証してください。サービスは Delcore に登録され、`authorize` スコープを持っている必要があります。ユーザートークン、未登録のサービス、このスコープを持たないサービスでは、テナント状態を読み取れません。

レスポンスには、リクエストした各テナント ID が送信順に含まれ、それぞれに次のいずれかの状態が付与されます。

| 状態                    | 意味                                                               |
| ----------------------- | ------------------------------------------------------------------ |
| `TENANT_STATE_ACTIVE`   | テナントが存在し、ブロックされておらず、削除処理中でもありません。 |
| `TENANT_STATE_BLOCKED`  | プラットフォーム運用者がテナントをブロックしました。               |
| `TENANT_STATE_DELETING` | 削除が保留中です。                                                 |
| `TENANT_STATE_DELETED`  | 削除が確定しています。                                             |
| `TENANT_STATE_UNKNOWN`  | Delcore にこの ID のテナントはありません。                         |

複数の条件に該当する場合、`DELETED` は `DELETING` より優先され、`DELETING` は `BLOCKED` より優先され、`BLOCKED` は `ACTIVE` より優先されます。

状態は請求に依存しません。サブスクリプションの期限切れ、更新の失敗、支払いに関する異議申し立て、残高不足によって、テナントが `BLOCKED` になることはありません。ユーザーが有料の処理を実行できるかどうかを判断するには、代わりに `Authorize` を使用してください。この確認はデータの読み取りのみを行います。テナントの変更、有料利用の承認、決済プロバイダーへの連絡は行わず、テナント名、ユーザーの詳細、請求情報も返しません。

## 結果と失敗の処理

- アクセスを許可するのは `TENANT_STATE_ACTIVE` の場合、または所有者や管理者向けに独自に文書化したルールで、ブロック済みまたは削除処理中のテナントへのアクセスが認められている場合のみとしてください。
- `TENANT_STATE_UNKNOWN`、リクエストエラー、タイムアウト、Delcore の利用不能は、アクセス不可として扱ってください。これらの場合にデータを削除しないでください。
- テナント削除に伴うクリーンアップでは、明示的な `TENANT_STATE_DELETED` を受け取った後にのみ、保持しているテナントデータを自動削除してください。`BLOCKED` と `DELETING` は、いかなる場合もこのクリーンアップを許可するものではありません。レコードの固定の有効期限は、テナント状態とは独立して適用されます。
- 無効な ID、空のリクエスト、100 個を超える ID は、引数無効エラーを返します。認証情報が欠落している場合、有効期限切れの場合、または無効な場合は、未認証エラーを返します。テナント状態の読み取りが許可されていない呼び出し元には、権限拒否エラーが返されます。その他の失敗では、相関 ID 付きのエラーが返されます。サポートを依頼する際は、エラーの詳細と `X-Delcore-Correlation-Id` ヘッダーに含まれるこの ID を添えてください。
- 失敗したリクエストは、後で再試行してください。リクエストの失敗が、テナントが有効または削除済みであることを意味することはありません。

## 従量料金とレコードの有効期限

従量単価は、既存のサブスクライバーを含むすべての顧客について、初回の実行開始時点で適用されます。その開始時刻を `IngestEvent` の `occurred_at` として報告し、実行の再試行や使用量の照合を通じて維持してください。価格変更は、それ以降に開始する実行に適用されます。配信の遅延や訂正があっても、元の価格の適用が維持されます。定期支払いの価格、選択された機能、付与された無料利用枠には、引き続きサブスクリプションの条件が適用されます。

リクエストの重複排除は、レコードの初回作成から 30 日間有効です。再試行しても、この期間は延長されません。有効期限が切れた後は、同じリクエストキーで新しい操作を開始できますが、その時点の権限、および独立した支払いやイベントの同一性確認の対象となります。受け付け済みの使用量イベントは、会計処理への影響が重複することを防ぐため、永続的な識別情報を保持します。

利用側のサービスは、実行や使用量が不明のままである場合や、報告が Delcore に届いていない場合でも、使用量の配信および照合レコードを初回作成から 30 日後に削除する必要があります。その有効期限までは配信の再試行と不明な使用量の照会を続け、期限が切れたら保留中の請求を断念してください。請求のために使用量を推定しないでください。これにより、請求可能な使用量が永久に失われることがあり、また、実行の重複排除キーの有効期限が切れると、新たな実行と請求が可能になることがあります。プラットフォームの監査レコードと運用ログも、作成から 30 日後に有効期限が切れます。これらの制限によって、Delcore がすでに受け付けた会計エントリが削除されたり、API キーの有効性が変更されたりすることはありません。
