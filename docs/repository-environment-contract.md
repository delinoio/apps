# Environment contract

Commit only non-sensitive configuration, immutable tool versions and safe service-local examples. Never commit real environment files, credentials, signing material, `.infisical.yaml`, legacy `.infisical.json` or `.dev-environment/`. Delcore and Git Tracker operator configuration belongs to their services under `servers/`. Commit only service-local safe examples; real configuration and credentials stay outside Git. The shells require no account credentials. Mobile release credentials belong to the protected `delitools-mobile` GitHub environment; configure its secrets, variables and branch restrictions in this repository before dispatch. Secret values cannot be retrieved or migrated through Git.

Release preparation uses repository Actions variable `DELINO_RELEASE_BOT_CLIENT_ID` and secret `DELINO_RELEASE_BOT_PRIVATE_KEY` for the GitHub App installed on `delinoio/apps`. DevBase and DeliTools each use their `<project>-production` environment with secret `CLOUDFLARE_API_TOKEN` and variables `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_PAGES_PROJECT`. Delino Site and Delino Docs share `delino-site-production`, which owns secret `CLOUDFLARE_API_TOKEN`, variable `CLOUDFLARE_ACCOUNT_ID`, and separate variables `CLOUDFLARE_PAGES_PROJECT_SITE` and `CLOUDFLARE_PAGES_PROJECT_DOCS` for their Pages projects. The `delino` release also uses `delino-site-production` variables `CLOUDFLARE_PAGES_PROJECT_GIT_TRACKER`, `PUBLIC_LOGTO_ENDPOINT` and `PUBLIC_LOGTO_APP_ID` (public values only). Its DevBase deployment uses the existing `devbase-production` environment and must be permitted there for `delino@v*` tags. Server image publication uses the workflow `GITHUB_TOKEN` and needs no stored credential. Server runtime configuration and secrets stay with the operator's deployment target, never in Git or workflow files. Configure environment approvals, allowed main/tag refs, Pages production branches and domains outside Git. See the [workflow contract](repository-workflow-contract.md#project-release-preparation) for permissions and release procedures. The shared protected `release-signing` environment owns release signing credentials, including `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_PASSWORD` and `APPLE_TEAM_ID`. Application-specific updater keys retain their application prefixes. FixKey requires no native-acceptance revision variable. The shared protected `release-publish` environment owns final publication approval. Mobile release credentials remain in their existing protected environment.

## Local development injection

Install the [Infisical CLI](https://infisical.com/docs/cli/overview), run `infisical login`, then run `infisical init` from the repository root to connect the checkout to the development project. Current CLI versions create `.infisical.yaml`; older versions create `.infisical.json`. Keep both root project configuration files local and uncommitted. The CLI still reads the deprecated JSON format and, starting with version 0.44.3, also creates a YAML file when it reads JSON. See the [project configuration reference](https://infisical.com/docs/cli/project-config). Each checkout needs its own project configuration; authentication stays in the CLI's local credential store.

Every app-local `dev` and `dev:*` script and API `dev` script wraps its development command with `infisical run --env=dev --project-config-dir=../..`. App scripts read the default secret path `/`. Delcore adds `--path=/delcore-api`; DevBase adds `--path=/devbase-api`; Git Tracker adds `--path=/git-tracker-api`. The CLI injects only the selected folder's `dev` variables into the command after `--`. Keep API credentials in their owning folders. This separates shared setting names such as `LISTEN` and prevents API credentials from entering frontend development processes. No project ID, token or secret value is embedded in a package script. Native development hooks invoke the same wrapped frontend scripts. CLI installation, authentication and access to the development project are prerequisites; injection failures stop startup.

Root `pnpm dev` resolves the local database URLs from `docker compose config --format json`, waits for Compose, then starts process-compose, which delegates to the workspace scripts through Turborepo. The reserved `DEV_COMPOSE_DATABASE_URLS` handoff is passed only to the three API development tasks; do not define it in Infisical or service environment files. Each workspace still fetches its Infisical variables after Turborepo starts its task.

After injection, the API development launcher applies the owning Compose database URL through `DATABASE_URL` with higher priority than Infisical, the parent shell and the service-local `.env`. Delcore loads the optional service-local `.env` from the working directory for every invocation, preserving its operator configuration behavior. DevBase and Git Tracker load that file only when their launcher passes `--dev-env`. The Node launcher does not parse the file. Injected/process variables, including explicitly empty values, take precedence. The launcher preserves all non-database settings and leaves the local file unchanged. No temporary JSON configuration is created. Database URLs and configuration contents must not be logged.

Delcore's required `MAX_METER_GROUPS` and `MAX_METER_GROUP_VALUES` metering bounds follow that same non-database setting precedence; supply them through the `/delcore-api` development folder or the service-local `.env`, because missing values stop startup. Each is a base-10 integer from 1 to 1,000,000; missing, non-integer, or out-of-range values stop startup. The server reads them once at startup, so a change needs a restart. They bound groups per tenant, meter, and billing period and distinct values per group; see [cardinality rejection](servers-delcore-api-contract.md#recovery-procedures) for their operational effects. Delcore's optional `CATALOG_DIR` follows that same non-database setting precedence: an Infisical or process value wins over the service-local `.env`, which wins over the default. It selects a local YAML directory only when `DEVELOPMENT=true`; the default is the repository's `servers/delcore-api/catalog` example, resolved as `catalog` when the API runs from `servers/delcore-api`. A set value is an absolute path or a path relative to the service working directory; it must not be `.`, contain surrounding whitespace, or contain a NUL byte, and an invalid value stops startup even outside development. The launcher does not rewrite or read it, and Turborepo passes it to the Delcore development task. Keep catalog declarations free of credentials; invalid, missing, or empty development directories stop API startup. See the [server catalog contract](servers-delcore-api-contract.md#development-catalog).

API development launchers always set the owning fixed loopback `LISTEN`: `127.0.0.1:8080` for Delcore, `127.0.0.1:46317` for DevBase and `127.0.0.1:46321` for Git Tracker. Shared parent variables, Infisical and service-local `.env` values cannot redirect these development listeners. Non-development server startup retains its configured listener.

Root database port overrides are resolved before Infisical injection, so remote database settings cannot redirect this local workflow. Direct service-local development and root `pnpm dev:portless` have no handoff and retain their existing configuration behavior.

Build, test, localization and release commands do not use this injection. Keep service, production and signing credentials out of frontend development secrets. Only public client configuration may enter browser bundles.

## Turborepo remote cache

Enable Remote Cache for the intended Vercel team, then create a team-scoped access token with access to that cache. Store its value as the repository Actions secret `TURBO_TOKEN`. Set the repository Actions variable `TURBO_TEAM` to the team's slug. These settings are separate from production and signing environments. Do not put token values in Git, package scripts, task hashes, frontend environment configuration or logs. Account provisioning and token creation require an authorized Vercel account; repository changes do not provision them.

Only trusted main push and main manual frontend preparation jobs receive the token. PR jobs and non-main manual jobs must not receive this write-capable credential, even when Turbo is configured for read-only access. Missing settings disable remote access while retaining local caching. See the [workflow contract](repository-workflow-contract.md#turborepo-remote-caching) for the read/write policy and local login/link commands. Local Turbo credentials stay in the CLI credential store; the linked team configuration under ignored `.turbo/` stays local. Root development does not use these credentials for Infisical injection.

Rust API development launchers pass the internal `--dev-env` flag to the compiled binary. The binary reads only its service-local `.env` with dotenvy expansion, preserving injected and explicitly empty process values. Compose and fixed listener overrides are already applied before that read. Normal Rust startup, migration and audit commands do not read environment files.
