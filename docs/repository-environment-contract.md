# Environment contract

Commit only non-sensitive configuration, immutable tool versions and safe service-local examples. Never commit real environment files, credentials, signing material, `.infisical.yaml`, legacy `.infisical.json` or `.dev-environment/`. Delcore and Git Tracker operator configuration belongs to their services under `servers/`. Commit only service-local safe examples; real configuration and credentials stay outside Git. The shells require no account credentials. Mobile release credentials belong to the protected `delitools-mobile` GitHub environment; configure its secrets, variables and branch restrictions in this repository before dispatch. Secret values cannot be retrieved or migrated through Git.

Release preparation uses repository Actions variable `DELINO_RELEASE_BOT_CLIENT_ID` and secret `DELINO_RELEASE_BOT_PRIVATE_KEY` for the GitHub App installed on `delinoio/apps`. DevBase and DeliTools each use their `<project>-production` environment with secret `CLOUDFLARE_API_TOKEN` and variables `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_PAGES_PROJECT`. Delino Site and Delino Docs share `delino-site-production`, which owns secret `CLOUDFLARE_API_TOKEN`, variable `CLOUDFLARE_ACCOUNT_ID`, and separate variables `CLOUDFLARE_PAGES_PROJECT_SITE` and `CLOUDFLARE_PAGES_PROJECT_DOCS` for their Pages projects. Configure environment approvals, allowed main/tag refs, Pages production branches and domains outside Git. See the [workflow contract](repository-workflow-contract.md#project-release-preparation) for permissions and release procedures. The shared protected `release-signing` environment owns release signing credentials, including `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_PASSWORD` and `APPLE_TEAM_ID`. Application-specific updater keys retain their application prefixes. FixKey requires no native-acceptance revision variable. The shared protected `release-publish` environment owns final publication approval. Mobile release credentials remain in their existing protected environment.

## Local development injection

Install the [Infisical CLI](https://infisical.com/docs/cli/overview), run `infisical login`, then run `infisical init` from the repository root to connect the checkout to the development project. Current CLI versions create `.infisical.yaml`; older versions create `.infisical.json`. Keep both root project configuration files local and uncommitted. The CLI still reads the deprecated JSON format and, starting with version 0.44.3, also creates a YAML file when it reads JSON. See the [project configuration reference](https://infisical.com/docs/cli/project-config). Each checkout needs its own project configuration; authentication stays in the CLI's local credential store.

Every app-local `dev` and `dev:*` script wraps its development command with `infisical run --env=dev --project-config-dir=../.. --`. The CLI fetches variables from the linked project's `dev` environment and default secret path `/`, then injects them into the child process. No project ID, token or secret value is embedded in a package script. Native development hooks invoke the same wrapped frontend scripts. CLI installation, authentication and access to the development project are prerequisites; injection failures stop startup.

Root `pnpm dev` delegates to these app scripts through Turborepo, so each app fetches its variables after Turborepo starts its task. Build, test, localization and release commands do not use this injection. Keep service, production and signing credentials out of frontend development secrets. Only public client configuration may enter browser bundles.
