# Environment contract

Commit only non-sensitive configuration, immutable tool versions and safe service-local examples. Never commit real environment files, credentials, signing material, `.infisical.yaml`, legacy `.infisical.json` or `.dev-environment/`. Delcore, Git Tracker, DevBase, DeliTools and Perfine operator configuration belongs to their services under `servers/`. Commit only service-local safe examples; real configuration and credentials stay outside Git. The shells require no account credentials. Native signing credentials belong to the repository-wide protected `release-signing` environment, and store/registry publication credentials belong to `release-publish`; configure their secrets, variables and branch restrictions in this repository before dispatch. Secret values cannot be retrieved or migrated through Git.

Release preparation uses repository Actions variable `DELINO_RELEASE_BOT_CLIENT_ID` and secret `DELINO_RELEASE_BOT_PRIVATE_KEY` for the GitHub App installed on `delinoio/apps`. All web apps share `delino-site-production`, which owns secret `CLOUDFLARE_API_TOKEN`, variable `CLOUDFLARE_ACCOUNT_ID`, and optional project overrides `CLOUDFLARE_PAGES_PROJECT_SITE`, `CLOUDFLARE_PAGES_PROJECT_DOCS`, `CLOUDFLARE_PAGES_PROJECT_GIT_TRACKER`, `CLOUDFLARE_PAGES_PROJECT_LANE`, `CLOUDFLARE_PAGES_PROJECT_DEVBASE` and `CLOUDFLARE_PAGES_PROJECT_DELITOOLS`. The default Pages project name is the app directory name. Release preparation for each web app verifies or creates its direct-upload Pages project on production branch `main`. Git Tracker also reads `PUBLIC_LOGTO_ENDPOINT` and `PUBLIC_LOGTO_APP_ID` (public values only). Lane builds with the default public API origin `https://lane.api.delino.io`. These shared environments must permit main-dispatched unified releases. Server image publication and Lane GitHub Release binary publication use the workflow `GITHUB_TOKEN` and need no stored credential. Lane binary publication shares `delino-site-production`; it publishes the npm archive as a GitHub download without npm registry credentials. Server runtime configuration and secrets stay with the operator's deployment target, never in Git or workflow files. Private deployment automation owns the dispatch App private key and uses an installation token restricted to this public repository with contents write (required by repository dispatch) and Actions read permissions. This repository stores only `RELEASE_DISPATCH_ACTOR_ID`, the numeric bot sender ID, and rejects missing or mismatched identities. Do not use the release commit bot identity as the dispatch identity unless that broader authority is explicitly intended. Never include the coordinator repository name, URL, private run/evidence links, secrets or internal targets in dispatch payloads or public logs. Payloads contain public release identity only. Keep frontend publication credentials here in their existing protected environment; server credentials do not enter this repository. Configure environment approvals, allowed main/tag refs, Pages production branches and domains outside Git. See the [workflow contract](repository-workflow-contract.md#project-release-preparation) for permissions and release procedures. DeliTools Android and iOS builds use `release-signing`; optional store uploads and Perfine registry/Action publication use `release-publish`. App-specific Android keys retain their app-prefixed secret names within the shared signing environment. Apple team ownership uses the existing shared `APPLE_TEAM_ID` secret. Do not create app-specific production or mobile environments.

## Local development injection

Install the [Infisical CLI](https://infisical.com/docs/cli/overview), run `infisical login`, then run `infisical init` from the repository root to connect the checkout to the development project. Current CLI versions create `.infisical.yaml`; older versions create `.infisical.json`. Keep both root project configuration files local and uncommitted. The CLI still reads the deprecated JSON format and, starting with version 0.44.3, also creates a YAML file when it reads JSON. See the [project configuration reference](https://infisical.com/docs/cli/project-config). Each checkout needs its own project configuration; authentication stays in the CLI's local credential store.

Every app-local `dev` and `dev:*` script and API `dev` script wraps its development command with `infisical run --env=dev --project-config-dir=../..`. App scripts read the default secret path `/`. Delcore adds `--path=/delcore-api`; DevBase adds `--path=/devbase-api`; Git Tracker adds `--path=/git-tracker-api`; DeliTools adds `--path=/delitools-api`; Perfine adds `--path=/perfine-api`. The CLI injects only the selected folder's `dev` variables into the command after `--`. Keep API credentials in their owning folders. This separates shared setting names such as `LISTEN` and prevents API credentials from entering frontend development processes. No project ID, token or secret value is embedded in a package script. Native development hooks invoke the same wrapped frontend scripts. CLI installation, authentication and access to the development project are prerequisites; injection failures stop startup.

Root `pnpm dev` resolves the local database URLs from `docker compose config --format json`, waits for Compose, then starts `pnpm exec turbo run dev` directly to run the workspace scripts. Each frontend and API `dev` script runs Portless after Infisical injection and owns its route registration. The reserved `DEV_COMPOSE_DATABASE_URLS` handoff is passed only to the six API development tasks; do not define it in Infisical or service environment files. Each workspace still fetches its Infisical variables after Turborepo starts its task.

After injection, the API development launcher applies the owning Compose database URL through `DATABASE_URL` with higher priority than Infisical, the parent shell and the service-local `.env`. Delcore loads the optional service-local `.env` from the working directory for every invocation, preserving its operator configuration behavior. DevBase, Git Tracker, DeliTools and Perfine load that file only when their launcher passes `--dev-env`. The Node launcher does not parse the file. Injected/process variables, including explicitly empty values, take precedence. The launcher preserves all non-database settings and leaves the local file unchanged. No temporary JSON configuration is created. Database URLs and configuration contents must not be logged.

Delcore's required `MAX_METER_GROUPS` and `MAX_METER_GROUP_VALUES` metering bounds follow that same non-database setting precedence; supply them through the `/delcore-api` development folder or the service-local `.env`, because missing values stop startup. Each is a base-10 integer from 1 to 1,000,000; missing, non-integer, or out-of-range values stop startup. The server reads them once at startup, so a change needs a restart. They bound groups per tenant, meter, and billing period and distinct values per group; see [cardinality rejection](servers-delcore-api-contract.md#recovery-procedures) for their operational effects. Delcore's optional `CATALOG_DIR` follows that same non-database setting precedence: an Infisical or process value wins over the service-local `.env`, which wins over the default. It selects a local YAML directory only when `DEVELOPMENT=true`; the default is the repository's `servers/delcore-api/catalog` example, resolved as `catalog` when the API runs from `servers/delcore-api`. A set value is an absolute path or a path relative to the service working directory; it must not be `.`, contain surrounding whitespace, or contain a NUL byte, and an invalid value stops startup even outside development. The launcher does not rewrite or read it, and Turborepo passes it to the Delcore development task. Keep catalog declarations free of credentials; invalid, missing, or empty development directories stop API startup. See the [server catalog contract](servers-delcore-api-contract.md#development-catalog).

API development launchers always set the owning fixed loopback `LISTEN`: `127.0.0.1:8080` for Delcore, `127.0.0.1:46317` for DevBase, `127.0.0.1:46321` for Git Tracker `127.0.0.1:46322` for DeliTools and `127.0.0.1:46323` for Perfine. Shared parent variables, Infisical and service-local `.env` values cannot redirect these development listeners. Non-development server startup retains its configured listener.

Root database port overrides are resolved before Infisical injection, so remote database settings cannot redirect this local workflow. Direct service-local development has no handoff and retains its existing configuration behavior.

DeliTools API configuration is owned by [its server contract](servers-delitools-api-contract.md#environment-configuration). Its secrets are `DATABASE_URL`, `CLIENT_SECRET` (its own Delcore machine-to-machine identity) and `AI_GATEWAY_API_KEY` (Vercel AI Gateway); they live in the operator's deployment target or the `/delitools-api` Infisical development folder and never in Git, workflow files, frontend environments or logs. Non-secret service settings use unprefixed shared names (`LISTEN`, `DELCORE_URL`, `DELCORE_RESOURCE`, `LOGTO_TOKEN_URL`, `CLIENT_ID`, `AI_GATEWAY_BASE_URL`) or the `DELITOOLS_` prefix (`DELITOOLS_SERVICE_ID`, limits, timeouts, delivery and alert settings, and `DELITOOLS_MODELS`, the path of a model-catalog file that contains no secrets). `DEPENDENCY_TIMEOUT` and `LOG_FORMAT` keep their shared names. The Turbo development task passes `DELITOOLS_*` and `AI_GATEWAY_*` to the DeliTools API only. DeliTools image publication reuses the workflow `GITHUB_TOKEN`; it adds no GitHub environment, secret or variable. API key secrets are bearer credentials issued by Delcore at runtime; they are never configuration and never appear in environment files.

Perfine API development uses the same server-only handoff and injection order. Its launcher executes the shared `perfine-api` binary at the fixed `127.0.0.1:46323` listener. Its Turbo task passes `SPACE_STORAGE_QUOTA_BYTES`, `SINGLE_UPLOAD_LIMIT_BYTES`, `REQUESTS_PER_MINUTE`, `CONCURRENT_CLOUD_EXECUTIONS`, `RUST_LOG`, `PERFINE_*`, `R2_*`, `ALERT_*`, shared identity/GitHub settings and telemetry variables only to the API. Keep operator credentials in the owning server configuration; no user AI credential is a server setting. See the [Perfine API contract](servers-perfine-api-contract.md).

Build, test, localization and release commands do not use this injection. Keep service, production and signing credentials out of frontend development secrets. Only public client configuration may enter browser bundles.

## Turborepo remote cache

Enable Remote Cache for the intended Vercel team, then create a team-scoped access token with access to that cache. Store its value as the repository Actions secret `TURBO_TOKEN`. Set the repository Actions variable `TURBO_TEAM` to the team's slug. These settings are separate from production and signing environments. Do not put token values in Git, package scripts, task hashes, frontend environment configuration or logs. Account provisioning and token creation require an authorized Vercel account; repository changes do not provision them.

Only trusted main push and main manual frontend preparation jobs receive the token. PR jobs and non-main manual jobs must not receive this write-capable credential, even when Turbo is configured for read-only access. Missing settings disable remote access while retaining local caching. See the [workflow contract](repository-workflow-contract.md#turborepo-remote-caching) for the read/write policy and local login/link commands. Local Turbo credentials stay in the CLI credential store; the linked team configuration under ignored `.turbo/` stays local. Root development does not use these credentials for Infisical injection.

Rust API development launchers pass the internal `--dev-env` flag to the compiled binary. The binary reads only the service-local `.env` at the exact working-directory path with dotenvy expansion and never searches ancestor directories, so an absent local file is optional and an ancestor `.env` is neither imported nor parsed, and it preserves injected and explicitly empty process values. Compose and fixed listener overrides are already applied before that read. Normal Rust startup, migration and audit commands do not read environment files.

## Lane development environment

Lane API settings belong to `servers/lane-api` and the `/lane-api` Infisical development folder. The `@servers/lane-api#dev` task depends on the shared server build and launches the compiled binary through Portless at `https://lane-api.localhost`. The launcher fixes `LISTEN` to `127.0.0.1:46326` and applies the Lane Compose database URL after Infisical injection. Direct service-local development uses its configured database URL. Root database reset includes Lane and runs migrations explicitly.

Only the Lane API task receives its identity settings, required input/rate limits, `LANE_*`, `APNS_*`, `FCM_*`, `WEB_PUSH_*` and alert settings. Keep provider credentials, signing keys and webhook encryption keys out of frontend variables. The Lane frontend retains port `46325`; only `PUBLIC_*` configuration may enter its browser bundle. Follow the [Lane API contract](servers-lane-api-contract.md) for startup validation and credential ownership.
