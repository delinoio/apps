# Delcore v1 protocol contract

## Scope

This contract belongs to `delinoio/apps`. Schemas and generated Go and TypeScript messages live together in `protos/delcore/v1`. Connect-Go bindings live in its `delcorev1connect` subdirectory.

## Runtime and Language

Protobuf package `delcore.v1`; generated Go clients and handlers use the root `github.com/delinoio/apps` module, consumed directly by local server packages in the same module. There is no separate SDK package or UI.

## Users and Operators

User clients, service-specific M2M clients and platform operators.

## Interfaces and Contracts

Expose typed Connect interfaces for user discovery, tenants, memberships, invitations, ownership transfer, groups, catalog, subscriptions, top-ups, usage, corrections, feature authorization, API keys, metering aggregates and status, ledger, audit, failed-job recovery and service tenant state. Every protected request checks current permissions. Mutations accept client-generated idempotency keys; repeated keys with different inputs fail within 30 days from first creation. Replays do not extend expiry; an expired request key is accepted as a new request subject to current authorization and any independent accounting identities. Enum values describe states, roles and failure reasons. Delcore entity IDs are UUID v7; provider IDs remain explicit external references. Decimal quantities and monetary values use canonical decimal strings, never floats. Public decimal inputs are limited to 64 characters; internal products and sums retain their full precision. Return correlation metadata on responses and errors. Lists have bounded pagination.

Catalog mutations reject invalid combinations as invalid-argument errors. `PutPlan` rejects a free plan that enables postpaid continuation, including the default free plan, because free tenants never have a Paddle subscription to collect postpaid usage. `CreatePrice` rejects an add-on price whose service differs from the service that owns the add-on, and a price that names an unknown add-on, before it writes any price or audit row. These checks apply to new requests only; existing plans and prices are not rewritten.

Catalog creation requires explicit stable keys. A mutation of an existing entity may omit its key and reuse the stored key for its ID. Prices also require explicit scoped keys. A price `id` identifies an immutable price version; `stable_id` identifies its scoped price key, and `active` identifies the version currently selected for that key. Plan and add-on reads expose their active version IDs and typed feature values. Tenant reads expose the selected plan version ID. `PutFeature` declares a service-scoped access, metered, or configuration feature. Access values use an explicit boolean, metered values use a nonnegative canonical decimal limit, and configuration values use the declared oneof type. `PutPlan` and `PutAddOn` replace feature values when `replace_feature_values` is true or values are supplied; an omitted value list without that flag preserves the current assignments. Their responses return the normalized feature values of the selected active version. `PutMeter` supplies a stable key and typed aggregation and filter fields. A `MeterFilter` uses `typed_values` with explicit string, number or boolean operands. Numeric comparisons require a number operand; existence takes at most one boolean and defaults to requiring presence. `GetCatalog` returns canonical typed operands. The retired untyped `values` field is reserved. The existing meter `name` is its stable metering key and must match `key`. An unchanged meter definition is idempotent; a changed definition for the same key is invalid. Numeric comparison filter values are stored as canonical decimals, so equivalent spellings such as `1.0` and `1.00` are the same definition. Every meter requires an explicit event type and aggregation; a sum also requires its numeric value attribute. `GetCatalog` returns catalog identities, meter definitions, feature definitions, active product versions, and immutable price-version rows.

`ChangeSubscription` accepts active price versions, or an empty price list for a free plan whose active version has no catalog prices, and rejects duplicate feature definitions across the selected base plan and add-ons. The service pins the corresponding product versions in the subscription intent. A checkout intent alone does not activate them. A confirmed payment or scheduled free-plan transition installs the pinned versions; renewal retains the current product benefits and recurring payment prices. Usage unit prices are resolved separately at the initial execution start for all subscribers. Returning to an earlier semantic catalog definition reuses its existing version. Reactivated usage unit prices apply to subsequent executions by existing subscribers as well as new subscribers, without changing selected features or included-usage grants. The [server contract](servers-delcore-api-contract.md#catalog-version-pinning) owns product version content and pinning; [call-time usage prices](servers-delcore-api-contract.md#call-time-usage-prices) owns the effective-price history.

`IngestEvent` accepts one `Event` with a service-scoped `event_key`, `event_type`, `occurred_at`, and a flat `attributes` map of `AttributeValue` scalars: `text`, `boolean`, or a canonical decimal `number` string. Nested objects, lists, and binary floats are not representable. Delcore assigns the event `id`; requests leave it empty and set `service_id` to the calling service. Consumers use the initial execution start for `occurred_at`, preserve it across execution retries and unknown-usage reconciliation, and report only measured usage. Delcore attributes the effective usage unit price at that start rather than the subscription's originally selected price version; corrections retain the attribution. The response returns the event ID and accepted `revision`; an original event is revision 1. Success means the event and its processing work are durable, not that aggregates changed. Identical content under the same key replays the original identity; different content returns `ERROR_REASON_EVENT_IDENTITY_CONFLICT`. `CorrectEvent` names the tenant, event key, `expected_revision`, and an `EventCorrectionKind`: `EVENT_CORRECTION_KIND_REPLACE` supplies a complete type and attribute map, and `EVENT_CORRECTION_KIND_CANCEL` supplies neither. A stale expected revision returns `ERROR_REASON_STALE_REVISION`; re-read the event with `GetEvent`, which returns the latest content, latest revision, cancellation state, and `applied_revision` for asynchronous processing progress. Other typed reasons are `ERROR_REASON_NO_MATCHING_METER`, `ERROR_REASON_INVALID_ATTRIBUTE`, `ERROR_REASON_CARDINALITY_EXCEEDED`, `ERROR_REASON_EVENT_NOT_FOUND`, `ERROR_REASON_EVENT_CANCELLED`, and `ERROR_REASON_REPORTING_WINDOW_CLOSED`. The [server contract](servers-delcore-api-contract.md#event-ingestion-and-asynchronous-metering) owns limits, admission accounting, processing, and retention, and its [rating section](servers-delcore-api-contract.md#rating-and-ledger-reconciliation) owns charges and ledger differences.

Metering uses `IngestEvent`, `CorrectEvent`, `GetEvent`, `ListMeterAggregates` and `GetMeteringStatus`. The retired quantity RPCs, `ListUsage`, their messages and `Usage` are removed. `LedgerEntry` reserves its retired `usage_id` field. This is a coordinated pre-release change: repository callers and the server change together, without a transition reader or deployed-data migration. See the [pre-release transition](servers-delcore-api-contract.md#pre-release-transition).

`AuthorizeRequest` adds an optional service-scoped `feature_key` and a flat `group_values` map of `AttributeValue` scalars. An empty feature key keeps the previous response exactly and omits `feature`; group values without a key are invalid. `AuthorizeResponse.feature` is a `FeatureAuthorization` with the feature ID, `FeatureKind`, `entitled`, and, by kind, the canonical decimal `limit`, the last applied `usage`, the current billing `period_start` and `period_end`, or the typed `configuration` value of the plan and add-on versions pinned at the request time. It is omitted when the permission check fails or the key is unknown. A metered feature of a paid plan without a recorded current billing period omits `usage` and the period bounds and appends `BLOCK_REASON_RENEWAL` when the reasons do not already contain it. New block reasons are appended to `reasons` after the existing ones: `BLOCK_REASON_FEATURE_UNKNOWN`, `BLOCK_REASON_FEATURE_NOT_ENTITLED`, and `BLOCK_REASON_FEATURE_LIMIT_REACHED`. Group values that do not name exactly a metered feature's group-by attributes, or that accompany an access or configuration feature, return `ERROR_REASON_INVALID_ATTRIBUTE`. Usage excludes accepted but unprocessed events, and authorization reserves nothing, so concurrent or lagging execution can exceed a limit. A metered `limit` applies to each group separately; it is independent of the included usage that rating shares once per tenant meter period (see [group limits and shared included usage](servers-delcore-api-contract.md#group-limits-and-shared-included-usage)).

`ListMeterAggregates` names a tenant, the meter's `service_id` and stable `meter_key`, an optional `period_at` instant (default: request time), and a `Page`. It returns the meter ID, `MeterAggregation`, billing period bounds, and `MeterAggregate` rows with flat `group_values`, decimal `value` and `sum` strings, and `int64` `event_count` and `distinct_count`. For this list, `Page.after_id` carries the opaque `next_after_id` of the previous page. `GetMeteringStatus` names a tenant, or no tenant for the service-wide operator view, and returns `int64` unapplied event, pending job, and failed job counts, `oldest_pending_at`, `lag_seconds`, per-category `MeteringFailureCount` entries, and the latest failure time and `MeteringFailureCategory`. Both are read-only views of asynchronous state: a successful `IngestEvent` or `CorrectEvent` does not imply updated results. The [server contract](servers-delcore-api-contract.md#feature-authorization-and-metering-queries) owns evaluation order, pinning, period, overspend, and access rules.

Occurrence timestamps use PostgreSQL microsecond precision. The service normalizes timestamps before hashing, storing and matching corrections. Prorated included quantities use a 0.000001 quantum; monetary products retain exact decimal precision until currency rounding.

Deletion and withdrawal return a failed precondition while a previously attempted subscription intent remains incomplete. Unattempted subscription intents, and intents that the provider definitively rejected without creating a subscription, are stopped atomically when deletion starts. A stopped rejected intent keeps its rejection category and cannot be retried.

Disabling automatic top-ups clears the settings and stops queued charges that never reached the provider in the same request. Charges that may have reached the provider, including a rejected charge that an operator retried, continue. Accepting a subscription cancellation stops the same unattempted charges.

Negative postpaid corrections carry forward against usage charges. Operators refund any remainder in Paddle on cancellation. Confirmed usage-line refunds clear the corresponding settlement balance; fixed subscription refunds do not clear usage debt.

Consumer services with the `authorize` scope may call `GetTenantStates` for 1 to 100 known tenant UUIDs. The response repeats each requested ID, in request order, with one `TenantState`: `TENANT_STATE_ACTIVE`, `TENANT_STATE_BLOCKED`, `TENANT_STATE_DELETING`, `TENANT_STATE_DELETED` or `TENANT_STATE_UNKNOWN`. `TENANT_STATE_UNSPECIFIED` is the proto3 zero value and is never returned. Overlapping conditions resolve as `DELETED` over `DELETING` over `BLOCKED` over `ACTIVE`. `BLOCKED` means operator blocking only; subscription expiry, renewal failure, dispute and balance conditions never change the state. `DELETING` means deletion is pending, `DELETED` means deletion is final, and an unknown tenant is `UNKNOWN`. The call is read-only, needs no user ID, and returns no tenant names, user details or billing data beyond the standard response metadata. Invalid IDs, an empty request or more than 100 IDs return `ERROR_REASON_INVALID_INPUT`; user tokens, unregistered services and services without the `authorize` scope return `ERROR_REASON_FORBIDDEN`.

Consumers treat `UNKNOWN`, request errors and unavailable state as no permission for access or destructive cleanup. Only an explicit `DELETED` permits automatic tenant-lifecycle cleanup of the consumer's retained tenant data; `BLOCKED` and `DELETING` do not. A consumer may use `BLOCKED` and `DELETING` to deny project-scoped service calls while applying its own documented management exceptions. `CheckTenantLifecycle` semantics, and `Authorize` semantics without a feature key, field numbers and enum values are unchanged; feature authorization only adds fields and block reasons.

Consumer services with the `authorize` scope may call `CheckTenantLifecycle` for up to 100 known tenant IDs. Only IDs whose deletion is finalized are returned. Unknown IDs and pending deletion do not authorize cleanup. The result contains no tenant names or personal information. Consumers fail closed on request errors and delete their own retained tenant data for tenant-lifecycle cleanup only after explicit finalization. Fixed record expiry does not require lifecycle finalization.

### API keys

Delcore provides reusable, service-neutral API keys. `CreateApiKey`, `ListApiKeys` and `RevokeApiKey` manage them with Logto user tokens; `AuthorizeApiKey` lets a registered consumer service verify and authorize a presented key. The protocol and runtime contain no consumer-service-, AI-, Gateway-, model-, translation- or extraction-specific types or branches. The [server contract](servers-delcore-api-contract.md#api-keys) owns the behavior.

- `ApiKey` carries `id` (UUID v7), `owner_kind`, `tenant_id`, `user_id`, `name`, `grants`, `created_at`, optional `expires_at` and optional `revoked_at`. It never contains the secret or its hash. `ApiKeyOwnerKind` is `API_KEY_OWNER_KIND_PERSONAL` or `API_KEY_OWNER_KIND_TENANT`; the unspecified value is invalid input. A personal key acts for its owner `user_id` inside the tenant. A tenant service key acts for the tenant independently of the issuing user, whose ID is kept for attribution and audit only.
- `ApiKeyGrant` names a registered `service_id` and the `capabilities` of that service. A key has 1 to 16 grants with unique services and 1 to 32 unique capabilities per grant, each of 1 to 100 bytes. A name has 1 to 100 bytes and is not blank. Every service must exist and every capability must be one the service declared, checked when the key is created. Grants and `expires_at` are fixed at creation; there is no update, renewal or rotation operation. To change them, create a replacement key and revoke the old one. An absent `expires_at` means the key is valid until revoked, subject to authorization. A present value must be in the future.
- `CreateApiKeyRequest` is a mutation with a client-generated `request_key`, a `tenant_id`, `owner_kind`, `name`, `grants` and optional `expires_at`. `CreateApiKeyResponse` returns the key metadata and `secret`. The secret has the form `dlk_<32 lowercase hexadecimal characters of the key ID>_<43 base64url characters of 32 random bytes>` and is returned once, by the first execution. The stored mutation response used for replay never contains it: replaying a request key within the 30-day replay window returns the same metadata with an empty `secret`, and the same key with different input fails. A lost secret cannot be recovered; create a new key and revoke the old one.
- `ListApiKeysRequest` names a tenant and an `owner_kind` and uses the standard `Page`. It returns key metadata, including revoked and expired keys, in stable ID order with `next_after_id`, and never secrets. `RevokeApiKeyRequest` is an idempotent mutation with a `request_key`, tenant and `key_id`; the response returns the key with `revoked_at`. Revocation takes effect for later authorization immediately.
- Management uses user tokens only. A caller manages personal keys when they are a current member of the tenant and only for their own keys. Tenant keys require the current tenant Owner or Admin role. A service (machine-to-machine) identity cannot create, list or revoke keys, and an API key never authenticates any Delcore operation. Non-managers receive `ERROR_REASON_FORBIDDEN`; revoking another user's personal key or an unknown key returns the Connect `not_found` code; creating a key beyond 100 active keys per owner scope, or in a tenant that is being deleted, receives `ERROR_REASON_PRECONDITION`; invalid IDs, grants, names, expiry or an unknown service or capability receive `ERROR_REASON_INVALID_INPUT`.
- `AuthorizeApiKeyRequest` is sent by a registered service with the `authorize` scope and carries the full presented `secret`, a `capability`, `paid`, and the optional `feature_key` and `group_values` of `Authorize`. Delcore takes the service from the authenticated service identity, never from the request, and evaluates only grants for that service, so a service cannot authorize another service's capabilities. A malformed, unknown, wrong, revoked or expired secret, or a secret of a deleted tenant, returns the Connect unauthenticated error with `ERROR_REASON_UNAUTHENTICATED`, so the response never leaks attribution for an invalid secret. For a valid secret, `AuthorizeApiKeyResponse` returns `allowed`, `reasons`, the optional `feature` of `Authorize`, and the attribution `key_id`, `tenant_id`, `owner_kind` and `user_id`. A key without a grant for the calling service and capability returns `allowed=false` with `BLOCK_REASON_PERMISSION`. A personal key additionally requires its user's current permission for the capability in the tenant; a tenant key is evaluated independently of its issuer's membership. Both require the current tenant and billing checks of `Authorize` when `paid` is set, using the same reasons. Callers fail closed for paid execution on any error.
- Services that already use `Authorize` keep its request, response and behavior unchanged; the key operations add messages and RPCs without changing field numbers or enum values.

## Storage

Request deduplication records, consumer usage-delivery/reconciliation records, platform audit records and operational logs expire 30 days after first creation regardless of processing state. Retrying or changing state never extends that boundary. Consumers delete unknown and undelivered usage at expiry, accepting lost charges and possible new execution after deduplication expiry; do not estimate usage to avoid that loss. Accepted delcore accounting, event identities and processing work retain their separate policies.

Wire messages are not the database schema. Historical pricing and usage identities survive replay and corrections. Server retention boundaries are owned by the [server contract](servers-delcore-api-contract.md). Validate changes that affect retention against the local server implementation and this wire contract.

## Security

User and M2M credentials cannot substitute for each other. API key secrets are bearer credentials: they are shown once, stored only as a hash, never logged and never replayed. Service reporting is scoped to the authenticated registered service. Operator changes require an audit reason. Consumer application URLs are operator-allowlisted. Payment callbacks do not authorize entitlements. Enabling automatic top-ups requires an active Paddle subscription; manual top-ups remain available without a subscription. Subscription cancellation suspends automatic top-ups; settings cannot re-enable them while cancellation is pending.

## Logging

Correlate responses and logs without exposing credentials or raw provider payloads.

## Build and Test

`protos/scripts/` owns shared Buf entry resolution and comparison-revision breaking checks under the [repository workflow](repository-workflow-contract.md).

Use the root Buf generation, lint, formatting, breaking and freshness checks. Generation must preserve schemas and instruction files in the shared output tree. Remove obsolete generated files when deleting or renaming schemas. The consumer example lives in `examples/delcore-client`; run `go test ./...` and `go build ./examples/delcore-client` here. Connect service contract tests against real PostgreSQL and mocked external services live under `servers/` in this checkout. Run affected server integration checks and report any unperformed checks in the pull request. Root `pnpm proto:generate` also generates TypeScript bindings beside the schemas. Git Tracker consumes them through the private `@delino/protos` workspace; do not publish a separate TypeScript SDK.

Connect-Go and Protobuf use the root pinned versions. Add delcore to the existing Buf input selection.
