# Delcore v1 protocol contract

## Scope

This contract belongs to `delinoio/apps`. Schemas and generated Go and TypeScript messages live together in `protos/delcore/v1`. Connect-Go bindings live in its `delcorev1connect` subdirectory.

## Runtime and Language

Protobuf package `delcore.v1`; generated Go clients and handlers use the root `github.com/delinoio/apps` module, consumed directly by local server packages in the same module. There is no separate SDK package or UI.

## Users and Operators

User clients, service-specific M2M clients and platform operators.

## Interfaces and Contracts

Expose typed Connect interfaces for user discovery, tenants, memberships, invitations, ownership transfer, groups, catalog, subscriptions, top-ups, usage, corrections, feature authorization, metering aggregates and status, ledger, audit, failed-job recovery and service tenant state. Every protected request checks current permissions. Mutations accept client-generated idempotency keys; repeated keys with different inputs fail. Enum values describe states, roles and failure reasons. Delcore entity IDs are UUID v7; provider IDs remain explicit external references. Decimal quantities and monetary values use canonical decimal strings, never floats. Public decimal inputs are limited to 64 characters; internal products and sums retain their full precision. Return correlation metadata on responses and errors. Lists have bounded pagination.

Catalog mutations reject invalid combinations as invalid-argument errors. `PutPlan` rejects a free plan that enables postpaid continuation, including the default free plan, because free tenants never have a Paddle subscription to collect postpaid usage. `CreatePrice` rejects an add-on price whose service differs from the service that owns the add-on, and a price that names an unknown add-on, before it writes any price or audit row. These checks apply to new requests only; existing plans and prices are not rewritten.

Catalog messages add stable keys and IDs without changing existing field numbers. A service, plan, or add-on request that omits `key` and names no existing identity derives a deterministic key from its accepted name: the lowercase name with spaces and underscores replaced by hyphens when that form is a valid key, otherwise a normalized slug with a hash suffix of the name. A price `id` identifies an immutable price version; `stable_id` identifies its scoped price key, and `active` identifies the version currently selected for that key. Plan and add-on reads expose their active version IDs and typed feature values. Tenant reads expose the selected plan version ID. `PutFeature` declares a service-scoped access, metered, or configuration feature. Access values use an explicit boolean, metered values use a nonnegative canonical decimal limit, and configuration values use the declared oneof type. `PutPlan` and `PutAddOn` replace feature values when `replace_feature_values` is true or values are supplied; an omitted value list without that flag preserves the current assignments. Their responses return the normalized feature values of the selected active version. `PutMeter` supplies a stable key and typed aggregation and filter fields. A `MeterFilter` takes its operands from either the untyped `values` strings or `typed_values`, never both: untyped values keep their earlier meaning (strings for equality and membership, one decimal for numeric comparisons, and an optional boolean for existence), and `MeterFilterValue` operands carry a string, number, or boolean kind so equality and membership can compare number and boolean attributes. An existence filter without an operand requires presence. `GetCatalog` returns the canonical form, which keeps every earlier untyped definition and its catalog version unchanged (numeric comparison operands as canonical decimals) and uses `typed_values` only for number or boolean equality and membership operands. The existing meter `name` is its stable metering key and must match `key`. An unchanged meter definition is idempotent; a changed definition for the same key is invalid. Numeric comparison filter values are stored as canonical decimals, so equivalent spellings such as `1.0` and `1.00` are the same definition. A request with only the service and name stores a defaulted `SUM` definition for a new key and returns the stored definition for an existing key. `GetCatalog` returns catalog identities, meter definitions, feature definitions, active product versions, and immutable price-version rows.

`ChangeSubscription` accepts active price versions and rejects duplicate feature definitions across the selected base plan and add-ons. `price_ids` may be empty only for a free plan version that has no catalog prices. The service pins the corresponding product versions in the subscription intent. A checkout intent alone does not activate them. A confirmed payment or scheduled free-plan transition installs the pinned versions; renewal retains the current selection. Returning to an earlier semantic catalog definition selects its existing version for future subscriptions without changing earlier tenants. The [server contract](servers-delcore-api-contract.md#catalog-version-pinning) owns version content and pinning.

`IngestEvent` accepts one `Event` with a service-scoped `event_key`, `event_type`, `occurred_at`, and a flat `attributes` map of `AttributeValue` scalars: `text`, `boolean`, or a canonical decimal `number` string. Nested objects, lists, and binary floats are not representable. Delcore assigns the event `id`; requests leave it empty and set `service_id` to the calling service. The response returns the event ID and accepted `revision`; an original event is revision 1. Success means the event and its processing work are durable, not that aggregates changed. Identical content under the same key replays the original identity; different content returns `ERROR_REASON_EVENT_IDENTITY_CONFLICT`. `CorrectEvent` names the tenant, event key, `expected_revision`, and an `EventCorrectionKind`: `EVENT_CORRECTION_KIND_REPLACE` supplies a complete type and attribute map, and `EVENT_CORRECTION_KIND_CANCEL` supplies neither. A stale expected revision returns `ERROR_REASON_STALE_REVISION`; re-read the event with `GetEvent`, which returns the latest content, latest revision, cancellation state, and `applied_revision` for asynchronous processing progress. Other typed reasons are `ERROR_REASON_NO_MATCHING_METER`, `ERROR_REASON_INVALID_ATTRIBUTE`, `ERROR_REASON_CARDINALITY_EXCEEDED`, `ERROR_REASON_EVENT_NOT_FOUND`, `ERROR_REASON_EVENT_CANCELLED`, and `ERROR_REASON_REPORTING_WINDOW_CLOSED`. The [server contract](servers-delcore-api-contract.md#event-ingestion-and-asynchronous-metering) owns limits, admission accounting, processing, and retention, and its [rating section](servers-delcore-api-contract.md#rating-and-ledger-reconciliation) owns charges and ledger differences.

The `ReportUsage` and `CorrectUsage` RPCs are deprecated with `option deprecated = true`; they and their request, response, and `Usage` messages stay declared with unchanged field numbers. The server no longer bills them: a registered service with `usage:write` receives `FAILED_PRECONDITION` with `ERROR_REASON_PRECONDITION` and a message that names `IngestEvent` or `CorrectEvent`, and other callers keep the forbidden result. Report former quantities as events: a meter declared without typed fields uses the compatibility definition, so a quantity of N on meter M is an event of type M with a numeric `quantity` attribute N. `ListUsage` and `LedgerEntry.usage_id` stay unchanged; rating entries have an empty `usage_id`. This is a coordinated pre-release change without a feature flag: repository callers move to the event RPCs together with the server, and no deployed usage is migrated. See the [pre-release transition](servers-delcore-api-contract.md#pre-release-transition).

`AuthorizeRequest` adds an optional service-scoped `feature_key` and a flat `group_values` map of `AttributeValue` scalars. An empty feature key keeps the previous response exactly and omits `feature`; group values without a key are invalid. `AuthorizeResponse.feature` is a `FeatureAuthorization` with the feature ID, `FeatureKind`, `entitled`, and, by kind, the canonical decimal `limit`, the last applied `usage`, the current billing `period_start` and `period_end`, or the typed `configuration` value of the plan and add-on versions pinned at the request time. It is omitted when the permission check fails or the key is unknown. A metered feature of a paid plan without a recorded current billing period omits `usage` and the period bounds and appends `BLOCK_REASON_RENEWAL` when the reasons do not already contain it. New block reasons are appended to `reasons` after the existing ones: `BLOCK_REASON_FEATURE_UNKNOWN`, `BLOCK_REASON_FEATURE_NOT_ENTITLED`, and `BLOCK_REASON_FEATURE_LIMIT_REACHED`. Group values that do not name exactly a metered feature's group-by attributes, or that accompany an access or configuration feature, return `ERROR_REASON_INVALID_ATTRIBUTE`. Usage excludes accepted but unprocessed events, and authorization reserves nothing, so concurrent or lagging execution can exceed a limit. A metered `limit` applies to each group separately; it is independent of the included usage that rating shares once per tenant meter period (see [group limits and shared included usage](servers-delcore-api-contract.md#group-limits-and-shared-included-usage)).

`ListMeterAggregates` names a tenant, the meter's `service_id` and stable `meter_key`, an optional `period_at` instant (default: request time), and a `Page`. It returns the meter ID, `MeterAggregation`, billing period bounds, and `MeterAggregate` rows with flat `group_values`, decimal `value` and `sum` strings, and `int64` `event_count` and `distinct_count`. For this list, `Page.after_id` carries the opaque `next_after_id` of the previous page. `GetMeteringStatus` names a tenant, or no tenant for the service-wide operator view, and returns `int64` unapplied event, pending job, and failed job counts, `oldest_pending_at`, `lag_seconds`, per-category `MeteringFailureCount` entries, and the latest failure time and `MeteringFailureCategory`. Both are read-only views of asynchronous state: a successful `IngestEvent` or `CorrectEvent` does not imply updated results. The [server contract](servers-delcore-api-contract.md#feature-authorization-and-metering-queries) owns evaluation order, pinning, period, overspend, and access rules.

Occurrence timestamps use PostgreSQL microsecond precision. The service normalizes timestamps before hashing, storing and matching corrections. Prorated included quantities use a 0.000001 quantum; monetary products retain exact decimal precision until currency rounding.

Deletion and withdrawal return a failed precondition while a previously attempted subscription intent remains incomplete. Unattempted subscription intents, and intents that the provider definitively rejected without creating a subscription, are stopped atomically when deletion starts. A stopped rejected intent keeps its rejection category and cannot be retried.

Disabling automatic top-ups clears the settings and stops queued charges that never reached the provider in the same request. Charges that may have reached the provider, including a rejected charge that an operator retried, continue. Accepting a subscription cancellation stops the same unattempted charges.

Negative postpaid corrections carry forward against usage charges. Operators refund any remainder in Paddle on cancellation. Confirmed usage-line refunds clear the corresponding settlement balance; fixed subscription refunds do not clear usage debt.

Consumer services with the `authorize` scope may call `GetTenantStates` for 1 to 100 known tenant UUIDs. The response repeats each requested ID, in request order, with one `TenantState`: `TENANT_STATE_ACTIVE`, `TENANT_STATE_BLOCKED`, `TENANT_STATE_DELETING`, `TENANT_STATE_DELETED` or `TENANT_STATE_UNKNOWN`. `TENANT_STATE_UNSPECIFIED` is the proto3 zero value and is never returned. Overlapping conditions resolve as `DELETED` over `DELETING` over `BLOCKED` over `ACTIVE`. `BLOCKED` means operator blocking only; subscription expiry, renewal failure, dispute and balance conditions never change the state. `DELETING` means deletion is pending, `DELETED` means deletion is final, and an unknown tenant is `UNKNOWN`. The call is read-only, needs no user ID, and returns no tenant names, user details or billing data beyond the standard response metadata. Invalid IDs, an empty request or more than 100 IDs return `ERROR_REASON_INVALID_INPUT`; user tokens, unregistered services and services without the `authorize` scope return `ERROR_REASON_FORBIDDEN`.

Consumers treat `UNKNOWN`, request errors and unavailable state as no permission for access or destructive cleanup. Only an explicit `DELETED` permits automatic cleanup of the consumer's retained tenant data; `BLOCKED` and `DELETING` do not. A consumer may use `BLOCKED` and `DELETING` to deny project-scoped service calls while applying its own documented management exceptions. `CheckTenantLifecycle` semantics, and `Authorize` semantics without a feature key, field numbers and enum values are unchanged; feature authorization only adds fields and block reasons.

Consumer services with the `authorize` scope may call `CheckTenantLifecycle` for up to 100 known tenant IDs. Only IDs whose deletion is finalized are returned. Unknown IDs and pending deletion do not authorize cleanup. The result contains no tenant names or personal information. Consumers fail closed on request errors and delete their own retained tenant data only after explicit finalization.

## Storage

Wire messages are not the database schema. Historical pricing and usage identities survive replay and corrections. Server retention boundaries are owned by the [server contract](servers-delcore-api-contract.md). Validate changes that affect retention against the local server implementation and this wire contract.

## Security

User and M2M credentials cannot substitute for each other. Service reporting is scoped to the authenticated registered service. Operator changes require an audit reason. Consumer application URLs are operator-allowlisted. Payment callbacks do not authorize entitlements. Enabling automatic top-ups requires an active Paddle subscription; manual top-ups remain available without a subscription. Subscription cancellation suspends automatic top-ups; settings cannot re-enable them while cancellation is pending.

## Logging

Correlate responses and logs without exposing credentials or raw provider payloads.

## Build and Test

`protos/scripts/` owns shared Buf entry resolution and comparison-revision breaking checks under the [repository workflow](repository-workflow-contract.md).

Use the root Buf generation, lint, formatting, breaking and freshness checks. Generation must preserve schemas and instruction files in the shared output tree. Remove obsolete generated files when deleting or renaming schemas. The consumer example lives in `examples/delcore-client`; run `go test ./...` and `go build ./examples/delcore-client` here. Connect service contract tests against real PostgreSQL and mocked external services live under `servers/` in this checkout. Run affected server integration checks and report any unperformed checks in the pull request. Root `pnpm proto:generate` also generates TypeScript bindings beside the schemas. Git Tracker consumes them through the private `@delino/protos` workspace; do not publish a separate TypeScript SDK.

## Dependencies and Integrations

Connect-Go and Protobuf use the root pinned versions. Add delcore to the existing Buf input selection.

## Change Triggers

Update this protocol contract and the [project index](project-delcore.md) when public interfaces change. Describe the interface change and validation results in the pull request. Update the local server contract and validate affected integration in the same change. Preserve field numbers and enum values.
