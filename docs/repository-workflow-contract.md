# Repository workflow contract

Generated protobuf and Connect bindings under `protos/` (`*.pb.go`, `*.connect.go` and `*_pb.ts`) are excluded from tokei counts through `.tokeignore` and from GitHub language statistics through `.gitattributes`. Schemas and hand-written files remain eligible for counting.

Root `pnpm dev` reads the resolved Compose configuration, runs `docker compose up -d --wait`, then registers named local URLs through Portless and starts process-compose to run the API tasks separately and the frontend tasks as a group through Turborepo with a server-only database configuration handoff. A Compose failure stops startup before any workspace task runs. The `dev` task is persistent and uncached. The current participants are DeliDev, DeliTools, DevBase, Delino Site, Delino Docs, FixKey and Git Tracker frontends, plus the Delcore, DevBase and Git Tracker Rust APIs. Each retains its documented fixed loopback port and fails on conflicts. The API launchers set each service's fixed `LISTEN` before the server starts, overriding shared parent variables and service settings for development. Stop the development session with `Ctrl+C`. App-local `pnpm dev` and `pnpm dev:desktop` remain available for individual frontend and native development. Each API also supports service-local `pnpm dev`. All API launchers execute the Rust binaries built by the shared `server-build` process. The builder watches Rust, Cargo, SQL and protocol inputs and restarts dependent APIs after a successful rebuild. Delcore loads its optional service-local `.env` for every invocation; DevBase and Git Tracker load it through `--dev-env`. Turborepo passes each API's unprefixed runtime settings to its development task, plus `ALERT_*` to Git Tracker and `OTEL_*` and `NO_COLOR` to all APIs. Configure the existing provider requirements before starting. Root development supplies the local database URLs to the APIs after Infisical injection. Root development provisions the Compose databases; schema migrations and provider credentials remain prerequisites. See the [Delcore server contract](servers-delcore-api-contract.md#local-development) and [Git Tracker server contract](servers-git-tracker-api-contract.md#local-development) for configuration. Each app-local `dev` and `dev:*` command and each API `dev` command injects the linked Infisical project's `dev` variables before startup. Install and authenticate the CLI and initialize the local root project configuration as described in the [environment contract](repository-environment-contract.md#local-development-injection). Root development delegates injection to each workspace task. YAML-only catalog edits do not restart Delcore; restart its API task to apply them.

Shared protocol tooling lives in `protos/scripts/`: `check-breaking.mjs` runs FILE breaking checks against a comparison revision, and `buf-entry.mjs` resolves the installed Buf Node entry for that check and CI. Run `node protos/scripts/check-breaking.mjs "<comparison-revision>"` from the repository root. Localization fixture tests live beside their implementation in `scripts/localization/`; root `pnpm test:tooling` includes them.

Changes under `servers/scripts/` select all three API entries in both server validation matrices.

## Process supervision

Install [process-compose](https://github.com/F1bonacc1/process-compose) before running root `pnpm dev`. The configuration uses the v1.122.0 CLI and schema. Root `process-compose.yaml` defines `server-build`, `frontends`, `delcore-api`, `devbase-api` and `git-tracker-api`. The application processes run the existing Turbo tasks, retaining environment allowlists and workspace-local Infisical injection. The shared server builder owns Rust rebuilds and dependent API restarts. A failed application task stops the session through `exit_on_failure`.

The single `server-build` process runs the server workspace Cargo build before any API starts and owns the cascading source watch. It skips compilation while the server workspace is empty. Install Cargo before root development. API processes wait for `process_completed_successfully`; ported launchers must run compiled binaries directly so they do not compete for the Cargo build lock. Build failures remain available for watch retries. See the [server Rust workspace contract](servers-rust-workspace-contract.md#shared-build-process) for inputs and scope.

Root development disables the process-compose HTTP control server so it does not conflict with Delcore's port 8080. It disables automatic dotenv loading so configuration continues through the existing environment owners. Process-compose owns child shutdown; `Ctrl+C` stops the processes and leaves Compose databases running. Root development disables the process-compose TUI by default because Portless starts its workspace command in a detached process group without foreground terminal control. Process logs remain visible. Use `pnpm dev delcore-api` to select a process after preparing the local databases. Extra root `dev` arguments now go to process-compose `up`, not Turbo. Service-local development retains its existing entry points. After Compose is ready, `scripts/dev.mjs` starts Portless, which discovers workspace `dev` scripts and invokes root `dev` with the internal `--supervised` argument. That argument enters process-compose directly, preventing recursive Portless startup and duplicate database preparation. User arguments are forwarded to process-compose after the internal argument. Process-compose retains task selection and supervision.

## Local development databases

Root `compose.yaml` provides separate PostgreSQL 17 instances for Delcore, DevBase and Git Tracker, matching the major version used by server integration CI. The frontends, native shells and Rust APIs run on the host through the existing development commands. Install Docker Engine and Docker Compose v2.20 or later, then start Docker. Root `pnpm dev` starts these databases automatically and waits for their healthchecks before launching process-compose. Existing containers and volumes are reused. `Ctrl+C` stops the development tasks and leaves the databases running for the next session. To start or inspect databases separately, run these commands from the repository root:

```sh
docker compose up -d --wait
docker compose ps
```

`--wait` waits for every database healthcheck to accept TCP connections. The probes use `127.0.0.1` inside each container so the PostgreSQL image's temporary socket-only initialization server cannot report readiness. To start only one database, append `delcore-postgres`, `devbase-postgres` or `git-tracker-postgres` to the `up` command. All databases publish only on `127.0.0.1`, use separate named data volumes and fail on port conflicts. The committed usernames and passwords are disposable local development values. Never use them for shared or production deployments.

- Delcore: `postgres://delcore:local-delcore@127.0.0.1:5432/delcore?sslmode=disable`
- Git Tracker: `postgres://git_tracker:local-git-tracker@127.0.0.1:55432/git_tracker?sslmode=disable`

`scripts/dev.mjs` owns root Compose orchestration and URL resolution; `servers/scripts/dev-api.mjs` owns the API environment overrides. Root `pnpm dev` derives these URLs from the resolved Compose service credentials, database names and published host ports. After Infisical injection, every API launcher receives `DATABASE_URL` with the owning Compose URL. Delcore loads its service-local `.env` with lower priority than injected/process variables for every invocation; DevBase and Git Tracker do so when their launcher supplies `--dev-env`. The Node launcher leaves the file to the binary. The launcher preserves all other settings and does not edit the local file.

For direct service-local development, set each API's `DATABASE_URL` to its corresponding local URL yourself. Keep the remaining provider and authentication configuration under the owning [Delcore](servers-delcore-api-contract.md#local-development), [DevBase](servers-devbase-api-contract.md#local-development) and [Git Tracker](servers-git-tracker-api-contract.md#local-development) contracts. Compose does not provision Logto, Paddle, GitHub or email provider accounts. Configure Infisical as described in the [environment contract](repository-environment-contract.md#local-development-injection); Delcore also supports its ignored service-local `.env`.

Delcore development startup also applies its [split-file YAML catalog](servers-delcore-api-contract.md#development-catalog) after the explicit schema check and instance lock, before it listens or processes jobs. The default example is committed at `servers/delcore-api/catalog`; set `CATALOG_DIR` for another local directory. This applies equally through root `pnpm dev` and service-local `pnpm dev`, because both start the same API through its Rust launcher. Catalog application does not change Infisical injection, the root database handoff and its precedence, the fixed listener, or single-instance enforcement; a second instance fails at the lock before reading the catalog. YAML edits alone do not restart the API; restart its task. Catalog synchronization is not a migration: run `migrate` explicitly first. Fix invalid declarations or database constraints before restarting; no partial set is committed. Delcore is pre-release, so its development database may be reset instead of migrated; see the [pre-release transition](servers-delcore-api-contract.md#pre-release-transition) for the reset commands and the [recovery procedures](servers-delcore-api-contract.md#recovery-procedures) for catalog and metering failures.

Initialize each empty database explicitly before the first API start. From the repository root, with Delcore settings in its service-local `.env` and `DATABASE_URL` pointing to the local database, run:

```sh
cargo build --locked --manifest-path servers/Cargo.toml --workspace --bins
(cd "servers/delcore-api" && ../target/debug/delcore-api migrate --dev-env)
DATABASE_URL='postgres://devbase:local-devbase@127.0.0.1:55433/devbase?sslmode=disable' ./servers/target/debug/devbase-api migrate
DATABASE_URL='postgres://git_tracker:local-git-tracker@127.0.0.1:55432/git_tracker?sslmode=disable' ./servers/target/debug/git-tracker-api migrate
pnpm dev
```

Delcore and DevBase track migration versions and checksums; rerun their migration commands after schema changes. Git Tracker currently embeds a single bootstrap SQL script with unconditional table and index creation. Run its migration command only once against an empty database. Do not rerun it on a retained volume after restarts or schema changes. Until upgrade migrations are supported, use a fresh disposable Git Tracker database for a changed schema; preserve any needed data before resetting its volume.

Database health does not establish schema readiness. Compose and root `pnpm dev` do not apply application migrations. Service-local `pnpm dev` can also use these databases; start Compose separately before using that command.

Inspect logs with `docker compose logs -f delcore-postgres devbase-postgres git-tracker-postgres`. Open a SQL session with one of these commands:

```sh
docker compose exec delcore-postgres psql -U delcore -d delcore
docker compose exec devbase-postgres psql -U devbase -d devbase
docker compose exec git-tracker-postgres psql -U git_tracker -d git_tracker
```

Stop and remove containers with `docker compose down`; the data volumes remain. `docker compose down --volumes` also deletes all local databases. After deleting volumes, start Compose and reapply the migrations.

For another checkout or occupied database ports, select an explicit project name and host ports on every Compose command. For example:

```sh
DELCORE_POSTGRES_PORT=15432 GIT_TRACKER_POSTGRES_PORT=15433 DEVBASE_POSTGRES_PORT=15434 docker compose -p apps-local-second up -d --wait
DELCORE_POSTGRES_PORT=15432 GIT_TRACKER_POSTGRES_PORT=15433 DEVBASE_POSTGRES_PORT=15434 docker compose -p apps-local-second down
```

When starting root development with that project, run `COMPOSE_PROJECT_NAME=apps-local-second DELCORE_POSTGRES_PORT=15432 GIT_TRACKER_POSTGRES_PORT=15433 DEVBASE_POSTGRES_PORT=15434 pnpm dev`. Root development derives the API database URLs from these ports automatically. Update the database URLs used by explicit migration commands and direct service-local development to the selected host ports. Each Compose project has its own data volumes. These overrides affect database ports only; application listeners retain their fixed ports, so concurrent worktrees cannot serve the same application on the host. PostgreSQL integration tests require separate disposable test databases through `TEST_DATABASE_URL`; do not point tests at databases containing development data.

See the Docker references for [Compose startup and healthchecks](https://docs.docker.com/compose/how-tos/startup-order/) and [PostgreSQL image storage and initialization](https://hub.docker.com/_/postgres).

Root development starts the Compose databases; prepare each API's schema and provider configuration before starting. Each task retains its Infisical injection and the API environment allowlists. Portless prefixes names with the branch in linked Git worktrees. Use the URLs printed at startup. Upstream ports remain fixed to preserve native shell development URLs and strict conflict handling; different worktrees cannot serve the same app concurrently on those ports.

Before the first session, run `pnpm exec portless proxy start` from an interactive terminal. Portless defaults to HTTPS on port 443, creates a local certificate authority, and can request administrator access to trust it and bind the port. This setup is local to the machine and is not an install hook. Non-interactive sessions must use an already prepared proxy. `Ctrl+C` stops the app session and removes its routes. The shared proxy remains available for other sessions. Inspect it with `pnpm exec portless list` or `pnpm exec portless doctor`; stop it with `pnpm exec portless proxy stop` when no session needs it. Portless keeps machine state outside the repository and can synchronize local host entries for browsers that need them. See the [upstream usage guide](https://github.com/vercel-labs/portless#readme) for trust and DNS troubleshooting. Rust APIs retain their separate startup commands, origins and authentication configuration.

### Git Tracker API configuration

The Git Tracker frontend also needs an API URL with the proxy's scheme and an exact matching allowed web origin. The direct-loopback values in the app and server `.env.example` files apply to direct development, not the Portless URLs. An HTTPS page cannot call the HTTP loopback API, and an HTTP Portless page still needs its own allowed origin.

Root `pnpm dev` starts the Git Tracker API through its Rust launcher and registers its route automatically. For the default HTTPS proxy in the main checkout, set `PUBLIC_GIT_TRACKER_API_URL=https://git-tracker-api.localhost` in the frontend's Infisical development configuration, or in the uncommitted `apps/git-tracker/.env.local` when the injected environment does not define it. Set `WEB_ORIGIN=https://git-tracker.localhost` in the API's Infisical development configuration, process environment or ignored service-local `.env`. Keep its other required settings under the [server contract](servers-git-tracker-api-contract.md). Restart the frontend and API after changing their settings. Portless does not supply credentials; the root development launcher provisions the Compose databases.

In a linked worktree, both web and API routes receive the branch prefix. Set `PUBLIC_GIT_TRACKER_API_URL` to the printed Git Tracker API origin and `WEB_ORIGIN` to the exact printed frontend origin. With the HTTP proxy on port 1355, the main-checkout API URL is `http://git-tracker-api.localhost:1355`; a linked worktree also includes its branch prefix. Include the scheme and any non-default proxy port, with no path or trailing slash. Register the frontend's `/callback` URL and sign-out origin in the development Logto application for the selected origin; authentication still requires its normal public application configuration.

When running the API separately without a root Portless session, an optional static route remains available after starting the proxy:

```sh
pnpm exec portless alias git-tracker-api 46321
```

This explicit alias has no automatic worktree prefix and persists until removed with `pnpm exec portless alias --remove git-tracker-api`. Remove an existing static alias before starting root `pnpm dev`, which manages its own routes and removes them on shutdown. Point the frontend at the static alias only while using that separate API workflow. Fixed upstream ports still permit only one local instance. Restore direct-loopback API and allowed-origin settings before returning to direct frontend development.

The local Delcore route supports server and command-line clients. The current Delcore handler does not provide CORS preflight responses or allow-origin headers, so browsers cannot make authenticated Connect calls to it from a different frontend origin. Do not set `PUBLIC_DELCORE_API_URL` to the local Portless origin for this workflow. Browser access to local Delcore requires separate CORS support; a registered Logto origin alone does not enable it. Keep `PUBLIC_DELCORE_RESOURCE` set to the resource identifier registered with Logto.

For server-to-server calls from Git Tracker to local Delcore, set `DELCORE_URL` to the printed Delcore API origin and retain its registered `DELCORE_RESOURCE`. Portless provides transport routing; it does not change resource identifiers or register development origins with identity providers. Follow the [Delcore server contract](servers-delcore-api-contract.md#local-development) for its remaining settings.

## Validation

The root `package.json` pins pnpm 12.14.0; the shared CI Node setup uses the same version and a version-specific store cache. Dependency overrides and build-script decisions are configured in `pnpm-workspace.yaml`, because pnpm 12 does not read the `pnpm` field in `package.json`.

Install with `pnpm install --frozen-lockfile`. Run `pnpm test` in each app, root `cargo test`, and `go test ./...`. Generate frontend `dist` before Rust validation, then remove generated `dist` directories. Native builds, device launches, account-backed integration and store acceptance are separate checks. Preserve source revision, commands, results and unperformed checks in commits and CI artifacts.

CI compares PRs with their base, pushes with the previous revision, and manual runs with the main merge base (or the parent on main). Manual validation remains affected-only. Ordinary CI runs on Ubuntu; macOS is restricted to the separate main-only mobile release workflow and the FixKey release workflow for tags verified to belong to main. Protocol validation includes Go vet, unit tests, consumer example builds and the DevBase TypeScript example type check; the dedicated formatting job checks Go formatting. Real PostgreSQL integration runs for the affected services under `servers/`. Ordinary CI does not run OCI tests or image builds. Protocol changes require lint, format, regeneration freshness and FILE breaking checks against the comparison revision.

Mobile dispatch preserves signed build-only mode and opt-in Google Play internal/TestFlight uploads. Configure the protected environment described in the application contract before use. Release workflows do not establish store acceptance until run with real accounts.

The Tauri wrapper consumes the immutable release and hashes in `prebuilt-dependencies.lock.json`. These shared binaries remain published by `delinoio/oss`; keep that producer URL and source pin unchanged. Local source builds are explicit; CI source fallback is forbidden.

Use root `pnpm format` and `pnpm format:check` for changed supported files. Lefthook formats staged files while preserving unstaged changes. CI runs `pnpm format:check --all` across all tracked supported files without change detection. Track assets of at least 512 KiB with exact-path Git LFS entries and hydrate them before builds. Schema-only baseline checks skip unrelated LFS smudging.

Delino Site and Delino Docs run offline translation coverage and source-fingerprint checks in their owning `pnpm test` and `pnpm build` commands. Root `pnpm i18n:check` checks all workspaces that provide that script; root `pnpm i18n:translate` generates translations for up to two participating workspaces concurrently. Root account commands share the same local ChatGPT session as app-local commands. Shared localization fixtures participate in root `pnpm test:tooling`. Project-specific helpers and tests live under their owning app: FixKey release tooling in `apps/fixkey-app/scripts/release/` and DeliTools mobile workflow fixtures in `apps/delitools/scripts/mobile-workflow.test.mjs`. Root `pnpm test:tooling` retains both fixture suites; FixKey `ci:check` and DeliTools `pnpm test` also run their owning suites. Translation generation and ChatGPT authentication are local maintainer operations under the [localization contract](apps-delino-site-localization-contract.md); CI and static deployment require no ChatGPT credentials.

Breaking validation compares directly against the selected Git revision without rewriting historical `go_package` options. Go package paths participate in the FILE breaking checks alongside wire compatibility.

CI retains separate `devbase-frontend`, `delino-site-frontend`, `delino-docs-frontend`, `delidev-frontend`, `delitools-frontend`, `fixkey-frontend`, `fixkey-desktop`, `rust-clippy`, `rust-test` and `protocol` jobs, plus independent `rust-servers-clippy` and `rust-servers` matrices for Delcore, DevBase and Git Tracker. The planner gates each project job before runner allocation. `check-formatting` (display name `Check Formatting`) owns all CI formatting checks: Rstack across all tracked supported files, both client and server workspace Rust formatting, and Go and Protobuf formatting. These checks and their toolchain setup always run without affected-path conditions or a dependency on the changes job. This job runs on Ubuntu and is required by `ci-result`. `validate` checks tooling fixtures, shared UI type/interaction/CSS tests and workflow syntax. Changes in `packages/ui` select all frontend consumers through the shared-path planner. `ci-result` fails if any selected job fails, is canceled, or is skipped. Unselected project jobs must remain skipped.

For `pnpm-lock.yaml`, the project planner reads both revisions from the exact event comparison before dependency installation. When only generated pnpm v9 importer blocks change, it selects their owners as package-manifest changes. Shared-workspace importer changes retain shared-path selection. Root importer changes, edits outside importer blocks (including package resolutions, snapshots and settings), unknown ownership, unsupported layouts and unavailable comparisons retain global project selection. This supports pnpm's multi-document lockfile, including its package-manager document. Other changed paths still contribute their normal selection.

Other root dependency locks select their owning runtimes rather than every project. `Cargo.lock` and `prebuilt-dependencies.lock.json` select the DeliDev, DeliTools and FixKey project jobs; `go.sum` selects protocol validation, which includes Go consumer examples. These files alone do not select unrelated frontend or server jobs. Other changed paths still add their normal selection, and unrecognized root lockfiles retain shared-path selection.

The changes job runs pinned cargo-mono twice against the planner base: `changed --direct-only` selects Clippy packages, and `changed` expands reverse workspace dependencies for Test. Each package list gates its own Rust job before runner allocation; empty lists skip the job. Workspace manifests and lockfiles retain cargo-mono global-impact handling. CI tooling, Cargo configuration, toolchain and shared prebuilt dependency changes select all Rust packages. `go.sum` alone does not select Rust validation. If cargo-mono resolves a different merge base from the event comparison, both checks conservatively select every workspace package. Frontend-only changes outside native crate directories do not select Rust checks.

Rust validation installs the Linux native dependencies, generates only the selected shells' frontend output, including FixKey when selected, runs all-target tests and all-target/all-feature Clippy with warnings denied. Rust formatting runs in `check-formatting`. Cache restores are available to PRs; pnpm and Cargo caches are saved only after successful main validation. Each validation job retains a JSON artifact with the source revision, commands, outcomes, and unperformed native/account checks; affected jobs also record their comparison. Protocol freshness rejects both tracked and untracked generated changes.

Server runtime validation runs in this checkout. `rust-servers-clippy` and `rust-servers` use Ubuntu runners and the independent server Cargo workspace for all three APIs. The planner emits only affected Rust services in the matrix and skips the job when the matrix is empty. Matrix entries run independently with `fail-fast: false` and retain separate validation artifacts with their service identity. Server and protocol changes select the affected service checks before runner allocation. Changes to `docs/protos-delcore-v1-contract.md` select Delcore server validation; changes to `docs/protos-devbase-v1-contract.md` select DevBase server validation; changes to `docs/protos-git-tracker-v1-contract.md` select Git Tracker server validation. `rust-servers-clippy` runs service-specific Cargo Clippy with all targets and warnings denied. The independent `rust-servers` job runs unit tests and PostgreSQL tests. Both jobs use the same affected-service matrix, retain separate validation artifacts and are required by `ci-result` when selected. Neither job installs Go or runs Go compatibility checks. OCI test commands remain available for explicit local packaging validation. Go formatting remains in `check-formatting`. `ci-result` rejects failed, canceled or skipped selected server jobs. Record source revision, comparison, commands, results and unperformed live-account checks in the same review and CI evidence. See the [repository boundary contract](repository-boundary-contract.md).

## Turborepo remote caching

Use Vercel Remote Cache for cached Turbo builds. Configure the repository Actions variable `TURBO_TEAM` and secret `TURBO_TOKEN` under the [environment contract](repository-environment-contract.md#turborepo-remote-cache). CI runs the frontend preparation builds in `fixkey-desktop`, `rust-clippy` and `rust-test` through `pnpm exec turbo run build:frontend --filter=<workspace>`. The existing affected-job and package gates remain in place. Frontend test commands and native Rust validation still execute normally; they are not cached by this integration.

Main pushes can read and write remote artifacts. Affected manual runs on main use remote reads only. PRs, including same-repository PRs, and non-main manual runs receive no remote cache token and use `TURBO_CACHE=local:rw`. The token itself grants write access; Turbo read-only options do not reduce its authorization and cannot protect it from PR-controlled commands. If either credential setting is absent, trusted main jobs also use local caching. This policy does not change pnpm or Cargo cache handling. Turbo uploads each successful build task independently of later job results. Credentials and cached logs must never contain account data or signing material.

Build tasks restore `dist/**` and include ignored `.env*` files in their inputs. FixKey extends the root frontend inputs with `$TURBO_EXTENDS$` before adding its package-specific root files, so the environment-file inputs remain inherited. Shared UI source, localization tooling, root license notices, the Node selector and pnpm workspace configuration participate in the global hash alongside the existing Go and protocol inputs. `NODE_ENV`, `PUBLIC_*`, `RUNNER_OS` and `RUNNER_ARCH` values also participate in the hash. CI artifacts are therefore isolated by runner OS and architecture; local runs without those runner variables use separate entries. Keep additional build-affecting environment variables and external files in the owning Turbo inputs before using them in cached builds. FixKey's native `build` task is uncached because its native artifacts are outside the frontend output contract. Development and test tasks remain uncached.

For local builds, run `pnpm exec turbo login`, then `pnpm exec turbo link` from the repository root and select the same Vercel team. Local authentication and `.turbo/config.json` remain uncommitted. Run `pnpm exec turbo run build:frontend --filter=<workspace>` to cache a frontend preparation build, or root `pnpm build` for the existing workspace build tasks. Remove the generated `dist` directories after validation. To bypass remote access, set `TURBO_CACHE=local:rw`; use `--force` to execute a task despite a cache hit. Login and link require interactive Vercel account access.

See the [upstream GitHub Actions guide](https://turborepo.dev/docs/guides/ci-vendors/github-actions) and [cache controls](https://turborepo.dev/docs/reference/run#--cache-options).

## Project release preparation

`.github/workflows/release-project.yml` follows the shared preparation and project-specific publication pattern. Dispatch it from `main`, select `devbase`, `delino`, `delitools` or `fixkey`, and choose `patch`, `minor` or `major`. Only the selected release's application versions change. The `delino` release calculates the next version from `apps/delino-site/package.json` and writes it to both that manifest and `apps/delino-docs/package.json`, regardless of their previous version agreement. Other web-only releases update their own npm manifest. DeliTools and FixKey also update their Tauri configuration, native package manifest and corresponding workspace `Cargo.lock` entry. The FixKey engine version is independent and is not bumped with the desktop application. Native source versions must agree before preparation.

`scripts/release/project.mjs` owns version calculation, source validation and the Git transaction. Preparation uses the release bot's identity, commits the selected files and atomically pushes `main` and its immutable tag. A concurrent main change or an existing tag rejects publication without moving the remote branch or tag. Preparation is serialized across projects. The commit records the workflow run ID and bump; rerunning the same run validates and reuses its recorded source even if main has advanced. Changed inputs, source contents or tags are rejected. Start a new run for a new version. Do not replace a tag or bypass branch protection to recover a failed run.

Tags are `devbase@vMAJOR.MINOR.PATCH`, `delino@vMAJOR.MINOR.PATCH`, `delitools@vMAJOR.MINOR.PATCH` and `fixkey@vMAJOR.MINOR.PATCH`. A GitHub App installation for this repository supplies `DELINO_RELEASE_BOT_CLIENT_ID` as an Actions variable and `DELINO_RELEASE_BOT_PRIVATE_KEY` as a secret. It requires contents write access and repository rules that permit its release commits and tag creation. The app token allows tag pushes to start the owning workflows; the default Actions token does not trigger that follow-up automation. Checkout temporarily retains the app credential for the atomic push and removes it during post-job cleanup. Registry package publication occurs only in the `delino` release workflow described under [Server image publication](#server-image-publication).

DeliDev has no release entry because its owning desktop contract removes distribution automation. Server runtimes live under `servers/`. Only the `delino` tag publishes their images; see [Server image publication](#server-image-publication). Release preparation itself does not publish images.

## Web publication

The individual `.github/workflows/release-devbase.yml`, `release-delino.yml` and `release-delitools.yml` workflows publish the corresponding web applications. Each starts from its release tag. `release-delino.yml` publishes `delino-site`, `delino-docs`, `devbase` and `git-tracker` in parallel from the same `delino@vMAJOR.MINOR.PATCH` tag and source revision. Source validation checks the `delino-site` and `delino-docs` package versions; `devbase` and `git-tracker` keep their own independent versions and are built from the tagged revision. The `devbase` application is also published by its own `release-devbase.yml`, which remains available for web-only releases. The former `delino-site@v*` trigger is retired. To retry a deployment without another bump, dispatch the individual workflow from `main` with the existing tag. A source job checks the tag format, version and main ancestry using the trusted main helper before allocating the protected deployment job. Each deployment job checks out the resolved immutable source revision, hydrates LFS objects, installs the frozen workspace and runs the app's `pnpm test` to check types and build the static output. The `delino` release workflow runs only the app's `pnpm build`.

The Delino deployment matrix keeps `fail-fast: false` so one app failure does not cancel the others. The Cloudflare uploads are not atomic; inspect every job and retry the existing tag if any fails.

The Delino Wrangler action sets `pnpm_config_ignore_workspace_root_check=true` only for its deployment step because the pinned action installs its CLI with `pnpm add` at the workspace root without `--workspace-root`. pnpm 12 requires the `pnpm_config_` prefix for this setting. This exception allows that temporary CLI installation without changing the workspace-wide pnpm configuration. Remove it when the action supports explicit workspace-root installation. The workspace build-script allowlist permits `workerd`, which Wrangler installs during deployment.

DevBase and DeliTools production deployments use the corresponding `<project>-production` GitHub environment with secret `CLOUDFLARE_API_TOKEN` and variables `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_PAGES_PROJECT`. The `delino` release shares the `delino-site-production` environment among Delino Site, Delino Docs and Git Tracker with secret `CLOUDFLARE_API_TOKEN` and variable `CLOUDFLARE_ACCOUNT_ID`. Its `CLOUDFLARE_PAGES_PROJECT_SITE`, `CLOUDFLARE_PAGES_PROJECT_DOCS` and `CLOUDFLARE_PAGES_PROJECT_GIT_TRACKER` variables select the marketing, documentation and Git Tracker Pages projects. The DevBase application in the same release deploys through its owning `devbase-production` environment and the `release-devbase` concurrency group, exactly like `release-devbase.yml`, so one reviewer gate and one serialized upload queue protect its Pages project. `devbase-production` must also permit `delino@v*` tags and main-dispatched recovery. Each matrix entry names its environment and concurrency group. The Git Tracker build also reads the public browser identifiers `PUBLIC_LOGTO_ENDPOINT` and `PUBLIC_LOGTO_APP_ID` from this environment. Without them the Git Tracker sign-in is not configured; the workflow does not validate them. These values are not secrets. The deployment matrix maps each application to its own variable for both configuration validation and upload. The token needs Cloudflare Pages edit permission for the owning account. Configure reviewers and deployment branch/tag restrictions to permit the owning project tags and main-dispatched recovery. `delino-site-production` must permit `delino@v*` tags and main-dispatched recovery. Create each Pages project with production branch `main` and bind its documented domain before publication. Disable automatic Git-based deployments if the Pages project already has Git integration, so source preparation does not also publish an untagged build.

The workflow includes repository `LICENSE` and `NOTICE`, retains the exact candidate as an artifact before upload, and uses a pinned Wrangler action and CLI to upload to the Pages production branch. Each project serializes deployments without canceling an active release. Source revision and version appear in the run summary; command and upload outcomes remain in the owning job logs. Generated frontend `dist` is removed even after failure. A failed upload can be retried with the existing immutable tag. Actual Cloudflare deployment, domain routing and account configuration require a real platform run; local fixtures and builds do not establish those outcomes.

## Server image publication

A `delino@vMAJOR.MINOR.PATCH` release also publishes the three server images. The `images` job runs after the shared source job, in parallel with the web publication. It builds `servers/delcore-api`, `servers/devbase-api` and `servers/git-tracker-api` from their Dockerfiles at the tagged revision and publishes `ghcr.io/<owner>/<server>:<version>` with the repository's `GITHUB_TOKEN`. Only this job holds `packages: write`. The image labels carry the source repository, version, revision and server license.

A release tag never moves, so a retry reuses an existing image tag instead of rebuilding it. Retry a failed run by dispatching `release-delino.yml` from `main` with the existing tag. The release does not deploy the images or run migrations; operators deploy them and apply migrations as the server contracts require. The Git Tracker migration is a one-time initial schema and is not repeatable. Make the published GHCR packages readable by the deployment target, either public or with registry credentials held by that target.

GHCR package creation and visibility have not been exercised against a real account. Record the first real release run as the platform acceptance evidence.

## Native publication handoff

Source preparation retains protected signing and publication gates. Preparing a FixKey version pushes its `fixkey@vMAJOR.MINOR.PATCH` tag and starts `release-fixkey.yml`. An unprotected Linux source job uses the trusted main helper to verify the tag format, version and main ancestry before allocating protected signing jobs or native runners. Native acceptance is recorded separately when performed; no native-acceptance revision variable or comparison blocks the workflow. To retry without another bump, dispatch `release-fixkey.yml` on main with the existing tag. All build and publication jobs check out the resolved tagged revision, including when main has advanced. Do not move the tag. Existing protected signing and publication environments, signed artifacts and immutable release checks remain required.

The DeliTools tag starts only its web publication. Dispatch `release-delitools-mobile.yml` on main separately with a new store build number and the desired platform. Signed build-only mode remains the default; Google Play internal testing and TestFlight uploads require explicit `publish`. Native builds, signing, device acceptance and store acceptance remain distinct from source preparation and web deployment.

Git Tracker client changes select `git-tracker-clients` on Ubuntu. The job checks the web app, Action tests/bundle freshness and shared generated bindings under `protos/`. Root `pnpm proto:generate` generates Go and TypeScript bindings together; both protocol and client freshness checks reject tracked and untracked changes in that tree. Protocol changes also select the client job because the web app consumes those schemas. Default manual validation remains affected-only.

Delcore, DevBase and Git Tracker use the [server Rust workspace](servers-rust-workspace-contract.md). Their development launchers execute compiled binaries. Delcore retains optional working-directory `.env` loading for every invocation; DevBase and Git Tracker load it only with `--dev-env`. Shared crate changes select all three Rust API matrix entries. Their Go service implementations, Go test oracles and Air configurations are removed; the root Go module continues to own generated protocol bindings and Go consumers.
