# AnyDash CLI and Collector Contract

## Scope

`cmds/anydash` (`implemented`) owns the Rust `anydash` executable. It is both the CLI and the single shared collector process: local session aggregation, provider polling, credential storage, upload, the local IPC service used by the desktop app, the CLI and desktop native widget hosts, local logs and the user service integration. It is a member of the root Cargo workspace and uses Apache-2.0. The [provider adapters contract](cmds-anydash-provider-adapters-contract.md) owns the provider matrix; the [protocol contract](protos-anydash-v1-contract.md) owns the wire format; the [distribution contract](packages-anydash-distribution-contract.md) owns archives, install scripts and `@delinoio/anydash`.

## Runtime and Language

Rust in the root Cargo workspace, `tracing` for logs, a pinned bundled SQLite driver for the local store, `zstd` for compressed session files and bindings generated from `protos/anydash/v1` by `cmds/anydash/build.rs` (install `protoc`). Rust is a documented exception to the repository's Go default for non-server projects so that the CLI and the desktop app's collector are one implementation. Supported collector platforms: macOS 14+ arm64 and x64; Windows 11 x64 and arm64; Ubuntu 24.04 and 26.04 and Debian 12 and 13, each x64 and arm64.

## Users and Operators

Individuals on desktops, servers and development machines with or without the desktop app; the desktop app, which embeds the matching `anydash` executable as its collector; desktop native widget hosts, which read widget snapshots from the collector; the maintainer, who reads `status` output and correlation IDs in support issues.

## Interfaces and Contracts

### Command surface

`anydash [--json] [--color auto|always|never] <command>`. Human-readable output is the default. `--json` prints one object, `{"ok":true,"result":{...}}` or `{"ok":false,"error":{"reason":"<ErrorReason value name>","message":"...","correlationId":"...","retryAfterSeconds":N}}`, using protocol enum value names and decimal 64-bit values. Exit code 0 means success, 1 an operation failure and 2 an invalid invocation. Results go to stdout and diagnostics to stderr.

Commands other than `run` and `service` operate through the local IPC service when a collector runs; the collector alone uses the device credentials, so `refresh <connection-id>` calls `RequestLocalConnectionRefresh`. Without a running collector they take the collector lock, perform the operation directly against the local store and the server, release the lock and exit without collecting. `status` without a running collector reports `run_state` from the stored state and states that the collector is not running. `connection list` lists the local connection status of `GetCollectorStatus`.

JSON results are canonical Protobuf JSON of the response messages (camelCase field names, enum value names, 64-bit integers as decimal strings) with default values included; the `status` result also carries `collectorRunning`. Human output prints IDs in full so that users can copy them. `status` reports `KEY_SOURCE_UNSPECIFIED` until the first secret creates a key.

Human output uses ANSI color when stdout is a terminal. `--color=never`, `NO_COLOR` or `ANYDASH_LOG_COLOR=never` disables it; JSON output never contains ANSI.

`ANYDASH_HOME` relocates the data, configuration and log directories (subdirectories `data`, `config` and `logs`) for isolated installs and tests. `ANYDASH_API_URL` overrides `https://anydash.api.delino.io` for development.

### Single shared collector

- One collector process runs per OS user and machine. It holds an exclusive advisory lock on `<data dir>/collector.lock`. The app and the CLI on one device share it, so they never collect twice. `service install` while a foreground or desktop collector runs fails with `INTERNAL` and asks the user to stop it first.
- Owners: `foreground` (`anydash run`), `service` (the installed user service) and `desktop` (started by the desktop app). The desktop app connects to a running collector; if none runs, it starts its embedded executable as `anydash run --owner desktop` in the background.
- Closing the app window does not stop collection. An explicit quit of the app calls `LocalCollectorService.Quit`, which stops a `desktop` or `foreground` collector. A `service` collector returns `SERVICE_MANAGED`; the app tells the user to use `anydash service uninstall` to stop it.
- Starting at login is opt-in: the desktop app setting registers a login item, and `anydash service install` registers the user service.
- The collector identifies itself to the API with `CLIENT_KIND_CLI` and its own version. One device identity exists per OS user and machine, whether the app or the CLI started enrollment.

### Local IPC

- Transport: the Connect protocol (HTTP/1.1, binary Protobuf) for `anydash.v1.LocalCollectorService` over a local stream socket.
- macOS and Linux: Unix domain socket `<runtime dir>/collector.sock` in a directory with mode 0700, socket mode 0600; the runtime directory is `$XDG_RUNTIME_DIR/anydash` on Linux (falling back to the data directory) and the data directory on macOS. The collector checks the peer user ID and rejects other users.
- Windows: named pipe `\\.\pipe\io.delino.anydash.collector.<user SID>` with a DACL that grants only the current user SID, and remote clients rejected.
- A client sends its first request over the connection that found the running collector. On Windows, a client retries an open that fails with `ERROR_PIPE_BUSY` (every pipe instance is in use, or the collector has not yet created its next instance) for up to 2 seconds before it reports the collector unreachable.
- No other process boundary is trusted. Requests carry no bearer token; the OS user boundary is the access control.
- Version skew: the app, CLI and embedded collector can have different versions. Clients read `CollectorStatus.collector_version`; an unknown method returns Connect `unimplemented`, and the client asks the user to update the older component.

### Refresh cadence

While the collector runs and is online:

- Local usage sync every 1 minute: scan session files, update local buckets and upload changed buckets.
- External polling every 5 minutes, only for connections whose valid lease this device holds.
- Heartbeat every 1 minute (`CollectorService.Heartbeat`, or the server's `heartbeat_interval`) with the collector version and ready connections; acquire the lease when `acquire_recommended`, renew a held lease with `RenewLease` before each poll and release leases on logout, disconnect, quit and stop signals. A provider poll can outlast the 5-minute lease and delays the next heartbeat, so while it runs the collector renews every held lease with `RenewLease` at the heartbeat interval; a lease lost during the poll abandons that poll without a report, and another lost lease returns its connection to candidate selection. A quit or stop signal during a cycle abandons the running provider poll without a report, skips the remaining polls and upload chunks, and releases the held leases without waiting for the provider. An active snapshot's `observed_at` is the UTC time, with microsecond precision, at which the provider poll completes, so it is never earlier than the lease's `acquired_at`, including on the cycle that acquires the lease. A local connection that no longer appears in the heartbeat assignments (deleted on the server or unregistered elsewhere) loses its local credential.
- Manual refresh once per minute per connection or device, from the app, `anydash refresh` or the server's `refresh_requested` and `local_sync_requested` flags. A request before then shows the remaining wait.
- Provider rate limits take precedence over every cadence.

If no collector device is running, external metrics stop refreshing.

### Failure handling and backoff

- A failed poll reports a snapshot with the failure status, so clients show the last successful value, its time and an error state from the first failure. Failure snapshots carry no resources. A subscription provider's failure snapshot carries the `FAILED` or `AUTH_EXPIRED` state for the provider's main metric keys. A deployment provider's (Vercel, Supabase, Cloudflare) failure snapshot carries no metrics, so the API marks every latest metric of the connection, including usage, cost and resource metrics, `FAILED` or `AUTH_EXPIRED` and keeps its last successful value. Each failure gets a local correlation ID shown per connection in `status`. Undelivered snapshots stay pending per connection and are retried under the same lease epoch; a pending snapshot of an older epoch is discarded. A snapshot the API rejects with `INVALID_ARGUMENT`, `NOT_FOUND` or `PAYLOAD_TOO_LARGE` is discarded, because the same payload cannot succeed. An active snapshot is kept within the `ReportSnapshot` limits (1,000 resources, 5,000 metrics including resource metrics, and the 1 MiB request body): account-level metrics are kept first, then resources in provider order while they fit; a `SUCCEEDED` snapshot that omits resources or metrics is reported as `PARTIALLY_SUCCEEDED`, so the omitted resources keep their previous values, and the collector logs `snapshot_truncated` with the omitted counts.
- Transient failures (timeout, network, provider 5xx, unreadable response, permission failure) use a 30-second request timeout and retry with exponential backoff: the n-th consecutive failure waits `min(30 minutes, 1 minute × 2^(n−1))` plus uniform jitter of up to 20% of that value, capped at 30 minutes. Retries are unlimited. A success resets the backoff.
- Provider rate limits follow provider guidance such as `Retry-After`. A `Retry-After` or backoff wait starts when the provider poll completes, not when the poll or the scheduler cycle started, so a slow poll or earlier connections of the same cycle never shorten it.
- Expired authentication stops that connection until the user reconnects. A stopped official token (Vercel, Supabase, Cloudflare) is not a usable credential: the device stops listing the connection as ready and releases a held lease, so another registered device with a valid token can take over; a lease that is still held because a release failed is released on the next due cycle without calling the provider. Reconnecting with a new token clears the stop and makes the device ready again. A reconnect or disconnect during a poll of that connection supersedes the poll: its result is neither reported nor stored, so a failure of the replaced credential never stops the new one, and lease or refresh updates read before the change never overwrite the new connection row. Local CLI credentials (Codex, Claude Code) are read again on every 5-minute cycle without calling the provider while expired, and polling resumes automatically when a valid credential appears. A credential is valid when it differs from the one that failed (SHA-256 credential-change marker) and its stored expiry (Codex access token `exp`, Claude Code `expiresAt`) is in the future. AnyDash never refreshes them. Grok authentication is the `grok` CLI's own; an unauthenticated `grok` is called again on the next regular cycle.
- AnyDash API failures (network, `DEPENDENCY_UNAVAILABLE`, `INTERNAL`) use the same backoff for the whole API cycle (heartbeat, upload and polls); local aggregation continues and buckets stay buffered. `RATE_LIMITED` waits `retry_after`; a rate-limited `UploadUsage` delays every upload until then, including uploads after manual, scheduled and server-requested local syncs, while those syncs still aggregate locally. `UPDATE_REQUIRED` stops every API call of that executable version, including heartbeats, while aggregation continues; the stored flag is cleared when a different version starts. `LEASE_EXPIRED` discards the pending snapshot and returns to candidate selection. `DEVICE_CREDENTIALS_INACTIVE` and `REFRESH_TOKEN_REUSED` stop upload and show that a new `anydash login` is required.
- Device access tokens are refreshed 5 minutes before expiry. The new refresh token is written to the secure store before the old one is discarded.

### Credential storage

- External credentials (official API tokens) and the AnyDash device credentials stay on the device. They are encrypted with AES-256-GCM using a 256-bit data key; ciphertext rows in the local store record the key ID (the first 8 bytes of the key's SHA-256, hex).
- Key source order: the OS secure store first (macOS Keychain item service `io.delino.anydash`, Windows Credential Manager target `io.delino.anydash/data-key`, Linux Secret Service through libsecret when a session bus and unlocked keyring exist). Where no GUI keychain exists, the key comes from the environment variable `ANYDASH_ENCRYPTION_KEY` (base64url of 32 bytes) or from the protected key file `<config dir>/encryption.key`, created with mode 0600; a key file readable by group or others is refused with `KEY_UNAVAILABLE`. The key file lives in the configuration directory, apart from the ciphertext in the data directory. `ANYDASH_KEY_SOURCE=os|env|file` forces one source. Unattended runs are supported with the environment variable or the key file.
- Manual rotation (`anydash key rotate` or the app settings): generate a new key, store it as the pending key, decrypt and re-encrypt all secrets in one SQLite transaction that also records the new key ID, then promote the pending key and delete the old key. If any step before the commit fails, delete the pending key and keep the old key and ciphertext (`KEY_ROTATION_FAILED`). After a crash between commit and promotion, startup completes the promotion using the recorded key ID. If the promotion fails after the commit (for example the OS secure store rejects the main-key write), the rotation returns `KEY_ROTATION_FAILED`, the running collector keeps using the new key for secret reads and writes, and the new key stays the pending key; the next rotation first completes that promotion and is refused with `KEY_ROTATION_FAILED` while the promotion still fails, so the pending key is never overwritten or deleted, and the next start also completes it. Secret reads and writes hold the data key through the store operation, so a rotation that runs concurrently (for example `key rotate` through IPC during a device token refresh) waits for them and never leaves a secret encrypted under a replaced key. With an environment variable source, the new key comes from `--new-key-env` and the user updates the environment afterward. Automatic rotation is not provided.
- Local CLI credentials (Codex `auth.json` or keyring service `Codex Auth`, Claude Code Keychain item or `.credentials.json`, the `grok` CLI login) are read in place on every cycle and never copied.
- With the OS store unforced, an existing key is used in the order OS store, environment variable, key file, so that existing ciphertext stays readable; a new key goes to the OS store when it is available and to the key file otherwise. The pending key is the OS item account `data-key-pending` or `<config dir>/encryption.key.pending`. A loaded key whose ID differs from the recorded key ID returns `KEY_UNAVAILABLE`.

### Storage

Directories (overridden by `ANYDASH_HOME`):

| Platform | Data                                                | Configuration                                    | Logs                                                           |
| -------- | --------------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------- |
| macOS    | `~/Library/Application Support/io.delino.anydash`   | `~/Library/Preferences/io.delino.anydash`        | `~/Library/Logs/io.delino.anydash`                             |
| Windows  | `%LOCALAPPDATA%\Delino\AnyDash\Data`                | `%APPDATA%\Delino\AnyDash`                       | `%LOCALAPPDATA%\Delino\AnyDash\Logs`                           |
| Linux    | `$XDG_DATA_HOME/anydash` (`~/.local/share/anydash`) | `$XDG_CONFIG_HOME/anydash` (`~/.config/anydash`) | `$XDG_STATE_HOME/anydash/logs` (`~/.local/state/anydash/logs`) |

The local store is SQLite `<data dir>/collector.db` in WAL mode with a schema version; an unsupported version stops the collector with an error and is never reset silently. It holds the retained device ID, encrypted secrets, source paths and their enabled state, file cursors and per-file bucket contributions, Claude Code deduplication keys, session start records, local 15-minute buckets with their current and uploaded versions, connection state (backoff, lease epoch, credential-change marker, account fingerprint), the latest pending snapshot per connection and native widget snapshots.

- Offline buffer: the collector keeps aggregating while offline or while uploads are rejected, keeps up to 90 days of buckets and uploads them automatically after reconnecting. Buckets older than 90 days are pruned and not recovered.
- The store holds only token counts, model identifiers, timestamps, hashed session identifiers and paths. It never stores prompts or response bodies. Paths and session identifiers are never uploaded.
- Original Codex and Claude Code session files are never modified or deleted.

### Session parsing

Paths, metrics and general parsing rules come from the [provider adapters contract](cmds-anydash-provider-adapters-contract.md#local-session-usage). Mechanics:

- Discovery: Codex reads `*.jsonl` and `*.jsonl.zst` under `$CODEX_HOME/sessions/` and `$CODEX_HOME/archived_sessions/` (`$CODEX_HOME` defaults to `~/.codex`). Claude Code reads `projects/**/*.jsonl` under each directory of `CLAUDE_CONFIG_DIR` (comma-separated) or, when unset, under `~/.claude` and `$XDG_CONFIG_HOME/claude` (`~/.config/claude`). A source path is a directory that is scanned recursively; `paths list` shows the detected `sessions`, `archived_sessions` and `projects` directories. User-added paths are absolute directories scanned with the same rules for their tool; disabled paths are skipped, and usage already aggregated from them remains. Directory symlinks are not followed.
- Cursors: each file has a cursor with its identity (device and inode, or the Windows creation time because the stable file index is not available through the Rust standard library), size, modification time and the byte offset after the last complete line. Growth resumes from the offset. Truncation, replacement or any change to a `.jsonl.zst` file re-reads the whole file and replaces that file's stored contributions. An incomplete last line is not parsed until it ends with a newline and does not count as unreadable.
- Buckets: each bucket's value is the sum of all file contributions for its tool, model and 15-minute UTC start. A Codex rollout holds one session, so files with the same Codex session ID are copies of one rollout (for example a rollout moved to `archived_sessions/` or compressed to `.jsonl.zst`); only the file with the largest token total counts, and contributions kept from the old path are not added again. When a value changes, its version becomes the current microsecond UTC time, forced above the previous version.
- Codex: each line is an object with `timestamp`, `type` and `payload`. `session_meta` gives the session ID (`payload.id`) and start time; the session is counted once, in the bucket of its start time (or of its first `token_count` record, identified by its file, when no `session_meta` exists). `turn_context.payload.model` sets the model for later token events; before it the model is `unknown`. For `event_msg` with `payload.type` `token_count`, `payload.info.total_token_usage` is cumulative per session: the delta is the current total minus the previous total of the same session, and a decreasing total starts a new baseline with `last_token_usage` as the delta. Codex `input_tokens` already includes cached tokens, so uncached input is `input_tokens − cached_input_tokens`, cache-read is `cached_input_tokens`, cache-write is `cache_write_input_tokens` when present and output is `output_tokens` (including reasoning). Tokens go to the bucket of the event `timestamp`. `payload.rate_limits` feeds passive Codex observations.
- Claude Code: entries with `type` `assistant` and `message.usage` are token records: `input_tokens`, `output_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens`, model `message.model` and the entry `timestamp`. Entries are deduplicated by `message.id` + `requestId` across all files of the device; an entry without `requestId` uses `message.id` with an empty request ID. When duplicates exist, the entry with the larger token total is kept and its timestamp selects the bucket. Each `sessionId` is counted once, in the bucket of its earliest entry. A counted session uses the first model known for it (Codex `turn_context`, Claude Code token entry) or `unknown`. Deduplication keys are kept for 90 days.
- Unreadable records (invalid JSON, or a token record with missing or malformed usage fields) are skipped and counted; readable records are still aggregated. A tool with skipped records reports `PARSER_STATE_PARTIAL` with `skipped_record_count` and shows the update notice.
- Backfill: the first scan after login reads records from the last 90 days only and uploads in chunks of at most 2,000 buckets and 1 MiB. Every `BucketResult` marks the sent version as uploaded; `INVALID` results are logged. A bucket whose sources vanish gets a new version with zero values so that the server receives the correction. Scanning and upload pause while the device is logged out; file cursors resume afterward.
- Copies of the same session files on several devices are aggregated independently on each device.

### Status output

`anydash status` (and `GetCollectorStatus`) shows: collector run state and owner; device ID; collector version; the correlation ID, reason and time of the last error; each connection ID with provider, display name, credential presence, lease state and epoch, last status, failure class, last success and next attempt; parser state and skipped record count per tool; last local sync and upload times; pending bucket count and the oldest pending bucket; key source; autostart state; login progress; and notices: a new version available, update required, and unsupported records (update the collector). Users can copy every ID. App error screens show the same correlation ID, device ID, connection ID and collector version.

### User service

- The definition carries `ANYDASH_HOME`, `ANYDASH_API_URL` and `ANYDASH_KEY_SOURCE` when they are set. `status` reports autostart as enabled when the definition exists (on Windows, the marker file `<config dir>/service-task`).
- macOS: LaunchAgent `~/Library/LaunchAgents/io.delino.anydash.collector.plist` with `RunAtLoad` and `KeepAlive`, loaded with `launchctl bootstrap gui/<uid>` and stopped with `launchctl bootout`.
- Linux: systemd user unit `~/.config/systemd/user/anydash-collector.service`, enabled with `systemctl --user enable --now`; the command prints how to enable lingering for servers without a login session.
- Windows: a per-user Task Scheduler task `AnyDash Collector` triggered at logon (`schtasks /Create /SC ONLOGON /RL LIMITED`), running `anydash.exe run --service`, which detaches from its console so no console window stays open.
- `service uninstall` stops the collector, releases leases and removes the definition. On macOS and Linux the stop signal lets the collector release its leases; on Windows `schtasks /End` terminates the process and its leases expire after 5 minutes. Installing when a foreground or desktop collector runs asks the user to stop it first.

### Update notices

`HeartbeatResponse.version_status` drives the notices. Logs and `status` show a new-version notice when `update_available`, an update-required notice when `update_required`, and an unsupported-parser notice when a tool reports `PARTIAL`. The notice names the install channel (install script, npm or desktop app update); there is no self-update.

## Security

- External credentials and device credentials never leave the device except to their own provider or AnyDash endpoints over HTTPS. They are never printed, logged or placed in errors.
- Official tokens are read from stdin or a named environment variable, never from command arguments.
- Uploads contain only aggregates; see the [server contract](servers-anydash-api-contract.md#local-usage-upload-and-aggregation).
- Local IPC is restricted to the current OS user.
- Logout releases held leases, then revokes the refresh token that is current after that release (releasing can rotate the device credentials; no rotation runs between revocation and deletion) and deletes the device credentials; `disconnect` deletes a provider token.

## Logging

- Collector logs are structured `tracing` events (key-value fields: time, level, event, correlation ID, device ID, connection ID, provider, tool, result category and duration), ANSI-colored by default with an opt-out (`--color=never`, `NO_COLOR` or `ANYDASH_LOG_COLOR=never`).
- They are written at level `info` to the OS log directory above as `anydash.YYYY-MM-DD.log` (UTC date, mode 0600), rotated daily and kept for 7 days or 50 MiB in total, whichever limit is reached first (oldest files are deleted first; the current file restarts empty when it alone exceeds 50 MiB). Every command writes to the log file; foreground runs also print to the terminal (stderr). The ANSI default applies to the log file and the terminal.
- Logs never contain secrets, tokens, prompts, response bodies, session contents or file contents. Paths are logged only as the tool and path origin.
- Local errors get a UUID v7 correlation ID, logged and shown in `status`.

## Build and Test

Run root `cargo test`, `cargo clippy` for the package and builds for every supported target. Required tests:

- Codex parser: cumulative deltas, cached-input handling, `.jsonl.zst` input, unknown `plan_type`, `rate_limits` extraction.
- Claude Code parser: `message.id` + `requestId` deduplication with largest-total selection, missing `requestId`.
- Unreadable records produce partial aggregation.
- 15-minute bucket aggregation and session counting in the start bucket.
- Collector: one shared process for the app and the CLI; collection continues after the window closes and stops on explicit quit; opt-in autostart and CLI service install and uninstall; key supply from the OS store, a 0600 file and an environment variable, atomic key rotation and rollback on failure; offline buffering for up to 90 days; log rotation at 7 days or 50 MiB.
- Backoff timing (1 to 30 minutes, jitter, 30-second timeout), `Retry-After`, authentication expiry and resume, lease acquisition, renewal and loss, `UPDATE_REQUIRED` buffering, and that no refresh-token request is ever sent to a provider.
- Enrollment from the CLI, logout keeping the registration and re-login reattaching the device.
- Human and JSON output, exit codes and color opt-out.

Cross-compilation does not establish installation or behavior on that OS; record native checks separately.
