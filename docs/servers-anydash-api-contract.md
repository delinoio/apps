# AnyDash API Contract

## Scope

`servers/anydash-api` (`implemented`) owns the Rust Connect API and the background worker that run in one process, PostgreSQL state and explicit forward migrations, OCI packaging, the load test and reusable operator assets under `servers/anydash-api/ops/` (monitoring rules, dashboards, rule fixtures and runbooks). Private operator automation owns infrastructure, rollout and deployment-specific monitoring settings. The package belongs to the independent server Cargo workspace and uses FSL-1.1-ALv2. This contract defines required behavior, not a deployed service. The [protocol contract](protos-anydash-v1-contract.md) owns the wire format; the [application contract](apps-anydash-foundation.md) owns product UX.

## Runtime and Language

Use Rust, the shared server crates (`servers/crates/server-common` for authentication, configuration, HTTP policy, rate limits and telemetry) and PostgreSQL 17. Consume the local `protos/anydash/v1` schema through `servers/crates/delino-protos`. The package is the explicit server workspace member `anydash-api` and the npm workspace `@servers/anydash-api`. Do not add a Go server or a second protocol repository. Use `tracing` for logs.

## Users and Operators

Signed-in users of the web, desktop and mobile clients; logged-in collector devices; Delcore as identity, tenant and role authority; the maintainer and operator, who configure the service, receive alerts, run the load test and approve releases. The server never calls AI or deployment providers; collectors do. Its only outbound calls are Logto key retrieval, Delcore and the LiteLLM pricing JSON.

## Interfaces and Contracts

### Routes and deployment boundary

- `https://anydash.api.delino.io/anydash.v1.DeviceService/<Method>`, `.../anydash.v1.CollectorService/<Method>`, `.../anydash.v1.ConnectionService/<Method>`, `.../anydash.v1.DashboardService/<Method>`, `.../anydash.v1.WidgetDataService/<Method>` and `.../anydash.v1.AccountService/<Method>`: Connect, gRPC and gRPC-Web.
- `/health/live`, `/health/ready` (database and configuration readiness) and `/metrics` (operator-only, bearer `ANYDASH_METRICS_TOKEN`).
- The API never serves `LocalCollectorService`.

The static web client is served at `anydash.delino.io` through Cloudflare Pages, including the enrollment approval page `https://anydash.delino.io/connect/<enrollment_id>`. CORS allows only `WEB_ORIGIN` and never arbitrary credentialed origins; native clients and collectors send no `Origin`. Requests that present an `Origin` other than `WEB_ORIGIN` are rejected with HTTP 403 before any handler runs.

### Identity and Delcore integration

- Logto owns identity. User tokens are Logto JWT access tokens for the resource `ANYDASH_RESOURCE` (`https://anydash.api.delino.io`). Validate the signature with the issuer's JWKS at `<LOGTO_ISSUER>/jwks` (cached for one hour, refreshed on an unknown key ID at most every 30 seconds; asymmetric algorithms only), `iss`, `aud`, `exp` and `nbf` with 30 seconds of leeway. Invalid credentials return `UNAUTHENTICATED`. JWKS retrieval failure returns `DEPENDENCY_UNAVAILABLE`, never a claim that the caller's token is invalid.
- `ConnectAccount` and `ListSpaces` receive a separate Logto token for the Delcore resource. Validate it the same way with the Delcore audience, require the same `sub` as the user token and call `delcore.v1.DelcoreService/GetCurrentUser` with it, following every `next_after_id` page. The personal tenant is the tenant with `personal=true` and `owner_id` equal to the returned `user_id`; reject a missing or ambiguous personal tenant. Never store or forward the Delcore token, never forward the AnyDash token to Delcore and never equate a Logto subject with a Delcore user ID. `ConnectAccount` stores the mapping from Logto subject to Delcore user ID and personal tenant.
- Register AnyDash in the Delcore catalog as a service with the `authorize` scope. The server's machine-to-machine identity (`CLIENT_ID`, `CLIENT_SECRET`, `LOGTO_TOKEN_URL`, `DELCORE_RESOURCE`) calls `GetTenantStates` and the role read below. AnyDash never reads Delcore tables.
- **Delcore role read.** The team role matrix needs the fixed roles of the caller and of widget data owners. `ListMembers` requires the Owner or Admin role of the caller, so Members cannot be classified through it. Delcore therefore provides the additive, read-only method `GetTenantMemberRoles` for registered services with the `authorize` scope: request `tenant_id` and 1 to 100 `user_ids`; response one entry per requested user in request order with `user_id`, `bool member`, `repeated Role roles` and `Timestamp member_since`. `member_since` is the start of the user's current membership; a user who leaves and rejoins the tenant receives a new value, and role changes keep it. A user who is not a current member, is withdrawing, or belongs to a deleted tenant is reported with `member=false`, no roles and no `member_since`. It returns no names or personal data and never writes state. The [Delcore protocol](protos-delcore-v1-contract.md) and [Delcore server](servers-delcore-api-contract.md) contracts own its behavior and tests. Existing Delcore tenant, role, `Authorize`, `GetTenantStates` and retention semantics stay unchanged.
- Every protected operation reads current state from Delcore within the request; it does not use a process-local authorization cache. It calls `GetTenantStates` for every space it touches (the caller's personal tenant for device, connection, account and collector operations, and the dashboard's tenant for dashboard operations) and requires `ACTIVE`. `BLOCKED`, `DELETING`, `DELETED` and `UNKNOWN` return `SPACE_INACTIVE`. Team operations call `GetTenantMemberRoles` for the caller and, for data queries, for every distinct data owner of the widgets in the response, batched in one call per tenant. Delcore errors return `DEPENDENCY_UNAVAILABLE` with a correlation ID and deny access.
- Collector operations (`CollectorService`, device-token `ConnectionService` calls) resolve the device's owner and require the owner's personal tenant to be `ACTIVE`. A blocked or deleting personal tenant stops collection uploads; collectors keep buffering locally.
- **User withdrawal.** Delcore withdrawal removes the user's personal tenant. When the worker's lifecycle sweep finds a user's personal tenant `DELETED`, it deletes all of that user's AnyDash data: devices, connections, usage, personal dashboards, widgets in team dashboards and shared widget data, following the deletion deadlines. A withdrawing user is already denied by the role read and tenant state checks.
- **Tenant lifecycle.** For a team tenant in `BLOCKED` or `DELETING`, all AnyDash activity in it stops: viewing, editing and the display of shared widget data. When a team tenant becomes `DELETED`, its team dashboards are deleted. Only explicit `DELETED` authorizes cleanup; errors and `UNKNOWN` never do.

### Authorization matrix

Authorization and tenant isolation are enforced on every RPC. Users, devices and spaces come from validated credentials, never from request ownership fields.

| Operation                                                          | Personal space user | Team Owner | Team Admin | Team Member | Billing-only or non-member |
| ------------------------------------------------------------------ | ------------------- | ---------- | ---------- | ----------- | -------------------------- |
| List and get dashboards, query widget data                         | Yes                 | Yes        | Yes        | Yes         | No                         |
| Create a dashboard                                                 | Yes                 | Yes        | Yes        | No          | No                         |
| Delete a dashboard                                                 | Yes                 | Yes        | Yes        | No          | No                         |
| Rename a dashboard, add a widget with own data                     | Yes                 | Yes        | Yes        | Yes         | No                         |
| Update position, size, title and presentation of any widget        | Yes                 | Yes        | Yes        | Yes         | No                         |
| Remove own widget                                                  | Yes                 | Yes        | Yes        | Yes         | No                         |
| Remove another user's widget                                       | Not applicable      | Yes        | Yes        | No          | No                         |

A user with several roles gets the union. Team-role edit permission never bypasses the data-owner rule. Every denial writes a `PERMISSION_DENIED` audit event.

### Sharing rules

- Personal connections and local usage reach a team dashboard only as the display data of widgets that their owner added. Team members can read only the `WidgetData` of those widgets; they cannot read the source connection, device list, other metrics, other periods or any other data. `WidgetSource` is returned only to the data owner.
- Widget data queries evaluate sharing on every call. Access ends immediately when the data owner revokes sharing, leaves the team or loses all of the Owner, Admin and Member roles (checked by the role read), deletes a source connection or device, deletes their AnyDash data or withdraws. The server persists `ENDED` with the matching `SharingEndReason` the first time it detects the condition; rejoining does not restore sharing. When the data owner adds a widget to a team dashboard, the server stores the owner's `member_since` from the role read with the widget; `SetWidgetSharingScope` replaces it with the current value when it shares the widget again. A later role read that reports a different `member_since` ends sharing with `OWNER_LEFT_SPACE`, so a departure and rejoin is detected even when no query ran during the absence.
- Clients and native widgets delete cached data for an `ENDED` widget at the next launch or refresh and show "sharing ended". Offline clients can show old data until then; data already displayed or saved separately cannot be revoked.
- Saving a dashboard checks its version. A concurrent edit returns `VERSION_CONFLICT`; nothing is merged.

### Enrollment and device credentials

- Enrollment codes expire 10 minutes after `StartEnrollment`, are used once and become invalid after 5 failed `ApproveEnrollment` attempts; the user must request a new code. The expiry also applies to an approved enrollment whose credentials no `PollEnrollment` delivered before `expires_at`: it becomes `EXPIRED`, and later polls return `ENROLLMENT_EXPIRED` without credentials. Store only SHA-256 digests of `device_code` and `user_code`. `StartEnrollment` is limited to 10 requests per minute per client IP address (the socket peer address, or the first address in `ANYDASH_CLIENT_IP_HEADER` when a trusted reverse proxy sets it); `PollEnrollment` to one request per 5 seconds per enrollment. Unused enrollment rows are deleted 24 hours after expiry.
- Approval binds the device to the approving Logto-authenticated user. `previous_device_id` reattaches only a device owned by the approving user; otherwise a new device is created.
- Credentials: access tokens `ada_` plus 32 random bytes in base64url, valid 1 hour; refresh tokens `adr_` plus 32 random bytes, rotated on every use. Store only SHA-256 digests. A refresh token expires 90 days after the device's latest accepted `UploadUsage` or `ReportSnapshot`. Keep digests of rotated refresh tokens for 90 days; presenting one returns `REFRESH_TOKEN_REUSED` and revokes all device credentials in the same transaction.
- Collector logout (`RevokeDeviceCredentials` with the refresh token) deletes the credentials and keeps the device registration and its data. Signing in again reattaches the same device.
- Reuse revocation, revocation with a user token and refresh expiry keep the credential digests with the non-`ACTIVE` device state, so the old tokens return `DEVICE_CREDENTIALS_INACTIVE` instead of `UNAUTHENTICATED`. Delivering credentials to a reattached device discards the rotated digests of its earlier credential generation, which then can no longer revoke the new credentials. Approval creates a new device in state `LOGGED_OUT`; the first poll sets `ACTIVE`.
- Deleting a device immediately revokes its credentials and its collection and upload rights.

### Collector leases, heartbeat and failover

- Each external connection has at most one valid lease, stored on the connection row with an increasing `lease_epoch`. All lease changes run in one transaction with `SELECT ... FOR UPDATE` on the connection row, so concurrent `AcquireLease` calls cannot grant two leases. A `Heartbeat` locks all connections it touches (registered for or leased by the device) in connection ID order before it extends any lease, so concurrent heartbeats of devices that hold different leases on the same connections cannot deadlock. Calls that change a device together with its connections or connection registrations (`Heartbeat`, `ReportSnapshot`, `RegisterConnectionDevice` and `UnregisterConnectionDevice`) lock the device row first, then the connection rows, then the registration rows, so concurrent calls for one device cannot deadlock.
- A lease is valid while `lease_expires_at` is in the future. Each `Heartbeat` and `RenewLease` by the holder sets `lease_expires_at` to 5 minutes later. Devices send a heartbeat every minute.
- When the holder sends no heartbeat for 5 minutes, the lease expires and collection moves to another registered device at its next heartbeat: first the user's preferred device, otherwise the device with the most recent heartbeat, among registered, online, `ACTIVE` devices that report the connection as ready. Ties go to the lower device ID. A preferred-device change does not preempt a valid lease.
- Results sent under an expired or superseded lease are rejected with `LEASE_EXPIRED`, including after the old device comes back. Deleting or unregistering a device, logout and connection deletion end its leases immediately.
- If no collector device is running, external metrics stop refreshing and the connection state becomes `NO_RUNNING_COLLECTOR`.
- Manual refresh is allowed once per minute per connection or device; the server records the request time on the connection or device row and delivers the request in the next heartbeat or renewal response.
- The connection row also keeps `last_holder_device_id`. A grant to a different device than the previous holder records `COLLECTION_DEVICE_CHANGED`; the `lease_expiry` job counts each lease it clears after expiry in `anydash_lease_failovers_total`.

### Local usage upload and aggregation

- Data minimization: the server accepts only aggregates per device, tool, model and 15-minute UTC bucket with session count, token counts by type and model identifier. It stores no per-session record, prompt, response body, path or per-project information.
- Uploads are cumulative per device, tool, model and bucket and carry a version. The upsert applies a bucket only when its version is greater than the stored version, so a resend of the same version is ignored and resends from the same device never add usage twice. Corrections within the last 90 days replace earlier values. Buckets older than 90 days are not accepted.
- A session is counted once, in the bucket where it starts; tokens are attributed to the bucket where they occur. The collector computes both; the server stores them as given.
- When the same session files exist on several devices, per-device totals are added together; there is no cross-device deduplication. Widget data carries the duplication notice.
- Hourly and daily views are computed at query time from 15-minute buckets in the selected IANA time zone, which stays exact for 30- and 45-minute offsets and DST transitions as defined in the protocol contract.
- The server stores the latest parser status per device and tool and the reported collector version.
- Timestamps from clients use the protobuf `Timestamp` range, years 1 to 9999 UTC, with valid nanoseconds. A present value outside that range, such as a `bucket_start`, parser `observed_at`, metric `period_start`, `period_end` or time value, returns `INVALID_ARGUMENT` for that field, so it is never stored as absent and never becomes a database error. An absent optional timestamp stays absent.

### External snapshots and hourly history

- Accept a snapshot only under the current valid lease epoch. For each reported metric (keyed by connection, resource ID or empty, kind and dimension):
  - The latest value changes only when the snapshot's `observed_at` is newer than the connection's latest observation. An older snapshot (`HISTORY_ONLY`) changes only hourly history, so it never restores resources or resource metrics that a newer snapshot removed. Failure and `AUTH_EXPIRED` states replace the latest state but keep the last successful value and its time.
  - For `VALUE` states, the hourly UTC snapshot for the hour of `observed_at` keeps the last successful value in that hour: a later observation in the same hour wins and an earlier one is ignored. A late result, for example after a collection-device change or a short offline period, lands in the bucket of its observation time, because a valid lease produced it.
  - Cumulative and instantaneous values are stored with their temporality and period and never mixed in one series.
- The resource set of a connection is replaced by each newer `SUCCEEDED` snapshot; resources missing from it and their resource metrics are removed from the latest view. A `PARTIALLY_SUCCEEDED` snapshot updates the reported resources without removing others.
- A newer `FAILED`, `RATE_LIMITED` or `AUTH_EXPIRED` snapshot without metrics marks the connection's latest metrics `FAILED` (failure class `RATE_LIMITED` for rate limits) or `AUTH_EXPIRED` and keeps their last successful values.
- The derived remaining percentage is `100 − used`, floored at 0 when a provider reports more than 100% used. Latest readings and hourly history both derive it from the used percentage of the same connection, resource and dimension, so a widget whose kind filter includes it, or that has no kind filter, returns a remaining-percentage reading or history series next to each used-percentage one.
- A daily metric history point is the last successful hourly snapshot observed in a local day of the selected time zone. Snapshots are grouped by the local date of their `observed_at`, not of their UTC hour, and snapshots observed before the query range starts are excluded, so a 30- or 45-minute offset never moves an observation into the adjacent day.
- Hourly snapshots are kept for 90 days.

### Estimated cost and LiteLLM price sync

- The worker fetches the LiteLLM pricing JSON (`model_prices_and_context_window.json`, from `ANYDASH_PRICING_URL`) daily at 03:00 UTC with a 30-second timeout, and retries hourly after a failure.
- Validation: the body is at most 20 MiB of valid JSON whose top level is an object with at least 100 model entries. For every entry the four used fields (`input_cost_per_token`, `output_cost_per_token`, `cache_read_input_token_cost`, `cache_creation_input_token_cost`) are absent or non-negative finite numbers. Any violation rejects the whole document.
- The normalized price set (model key and the four prices, sorted) is hashed with SHA-256. A new price version is created only when the hash differs from the current version; its `effective_from` is the fetch time. The earliest version also applies to all usage before it. If a fetch fails or validation fails, the previous version stays in use and the failure is recorded for alerting.
- Each bucket uses the price version in effect at its `bucket_start`. The cost is computed when the bucket is written and stored with the version ID. A new price version never recalculates past buckets; a corrected bucket is recomputed with the same pinned version.
- Model matching: the exact LiteLLM key first, then `openai/<model>` for Codex and `anthropic/<model>` for Claude Code. Required token counts: Codex input, output and cache-read; Claude Code input, output, cache-read and cache-write. A bucket whose model has no price, or that lacks a required count or a price for a non-zero count, is "cannot be calculated". Costs are in USD with no currency conversion.

### Deletion and data lifecycle

- Deleting a connection, device or dashboard, `DeleteAccountData`, user withdrawal and tenant deletion set `deleted_at` and block access immediately in the same transaction, then enqueue a deletion job with a deadline 24 hours after the request. The worker physically deletes the data from the primary database before the deadline. Backup copies expire with the backup retention period, which is at most 30 days.
- Deleting a connection deletes its stored latest values, hourly history, resources, device registrations and lease, and removes it from widget sources; widgets left without a source become `ENDED` with `SOURCE_DELETED`.
- Deleting a device deletes its local usage buckets, parser status, credentials and connection registrations, and removes it from widget sources. External connection history stays with the connection. If the device was a connection's last registered device, that connection stops refreshing.
- Deleting a dashboard deletes its widgets and their sources.
- `DeleteAccountData` and withdrawal delete all of the user's devices, connections, usage, personal dashboards, widgets in team dashboards and activity visible only to the user. The deletion job removes every team-dashboard widget the user owned at the request, including widgets whose sharing had already ended for another reason; widgets added after a `DeleteAccountData` request are not part of it. The account mapping row remains after `DeleteAccountData` so that the user can start again; withdrawal deletes it.
- Tenant `DELETED` deletes that tenant's team dashboards.
- `DeleteAccountData` and withdrawal end the user's widgets in team dashboards immediately with `OWNER_DATA_DELETED` and remove their sources, so team members see "sharing ended" until the deletion job removes the widgets. User-visible activity older than the deletion request is deleted; the `ACCOUNT_DATA_DELETION_REQUESTED` event remains until its 30-day expiry.
- The server never deletes or requests deletion of session files on devices.

### Quotas and rate limits

- Quotas, checked in the mutating transaction under a lock on the account or dashboard row: 20 collector devices and 50 external connections per user, 50 dashboards per space, 100 widgets per dashboard. Excess requests return `QUOTA_EXCEEDED` with `QuotaInfo`.
- Rate limits: 600 requests per minute per user token (keyed by Delcore user ID) and 60 per minute per device token (keyed by device ID), counted in fixed 60-second windows in PostgreSQL so that every replica shares them. `RefreshDeviceToken` and refresh-token `RevokeDeviceCredentials` count toward the device limit only after the current or a rotated refresh token of that device is authenticated; invalid refresh tokens count instead toward 60 per minute per client IP address, and once that window is full every refresh-token request from the address returns `RATE_LIMITED` with scope `DEVICE_TOKEN` before the token is checked. Unauthenticated enrollment limits are listed above. Excess requests return `RATE_LIMITED` with `retry_after` before the handler runs. One request body can be at most 1 MiB (`PAYLOAD_TOO_LARGE`). Each request has an absolute 60-second deadline that starts when its headers are received and covers body upload and handling: a body that has not arrived completely by then returns HTTP 408, and a handler that has not finished returns HTTP 504.

### Minimum client version

`ANYDASH_MIN_CLIENT_VERSIONS` sets the minimum SemVer per `ClientKind`. The check runs before authentication on every API request. Older clients receive `UPDATE_REQUIRED`; the collector keeps aggregating locally for up to 90 days. `ANYDASH_LATEST_CLIENT_VERSIONS` feeds the update notices in `HeartbeatResponse`.

### Audit events and user activity log

Record audit events for device enrollment, reattachment, logout, credential revocation (including reuse revocation) and deletion; enrollment invalidation; connection create and delete; connection device registration changes and collection-device changes; dashboard creation and deletion; share and unshare (including sharing ended by leaving, deletion or data deletion); permission denials; and account data deletion requests. Each event stores its kind, time, actor user or device, affected space, device, connection, dashboard and widget IDs, correlation ID and client kind, never secrets or usage values. Events expire 30 days after creation under the cross-service retention policy.

The user-visible activity log (`ListActivity`) covers the same 30 days. Users see events for their own devices, connections and account. Team Owners and Admins see events for team dashboards and sharing in that space.

### Background worker

The worker runs in the API process. Each job takes a PostgreSQL advisory lock so that only one replica runs it at a time. The `worker_job_runs` table stores the last start, success and failure of each job, so cadences are shared by every replica. The price sync is due once per daily 03:00 UTC window; on a database without a successful sync in the current window it runs at the next worker tick, and after a failure it waits one hour.

| Job                 | Cadence                          | Work                                                                                                                                                                                                                                                                                                       |
| ------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lease_expiry`      | Every 30 seconds                 | Clear expired leases and count failovers                                                                                                                                                                                                                                                                   |
| `deletion`          | Every minute                     | Physically delete data of pending deletion jobs; mark completion                                                                                                                                                                                                                                           |
| `retention`         | Hourly                           | Delete usage buckets, hourly snapshots, rotated refresh token digests and parser statuses older than 90 days, audit events, price sync runs and completed deletion jobs older than 30 days, request IDs older than 24 hours, enrollments 24 hours after expiry and rate-limit windows older than 2 minutes |
| `tenant_lifecycle`  | Hourly                           | Call `GetTenantStates` in batches of 100 for known personal and team tenants; enqueue withdrawal and team dashboard deletions for `DELETED`                                                                                                                                                                |
| `credential_expiry` | Daily                            | Mark devices `EXPIRED` whose refresh tokens passed the 90-day inactivity limit                                                                                                                                                                                                                             |
| `price_sync`        | Daily at 03:00 UTC, hourly retry | Fetch, validate and version LiteLLM prices                                                                                                                                                                                                                                                                 |

### Widget data details

- `WidgetQuery.metric_kinds` filters only kinds applicable to the widget type: `SUBSCRIPTION_LIMITS` and `SUBSCRIPTION_HISTORY` use the `SUBSCRIPTION_*` kinds and `PLAN_DOCUMENTED_QUOTA`; `DEPLOYMENT_USAGE` uses the `DEPLOYMENT_*` kinds except the two cost kinds, plus `PLAN_DOCUMENTED_QUOTA`; `DEPLOYMENT_COST` uses `DEPLOYMENT_BILLED_COST` and `DEPLOYMENT_EFFECTIVE_COST`; `DEPLOYMENT_RESOURCES` uses the deployment kinds; `METRIC_HISTORY` uses every kind. Other kinds return `INVALID_ARGUMENT`. `SUBSCRIPTION_LIMITS` and `SUBSCRIPTION_HISTORY` read account-level metrics only. A nonempty `resource_ids` filter applies to every reading and history series, so it also excludes account-level metrics, which have no resource ID. Local usage widgets accept 1 to 20 `device_ids` or `all_devices` (all of the owner's current devices).
- Local usage series and metric history return one point per local hour or day of the range, including zero-usage points. Buckets are included when their start is at or after the 15-minute boundary at the range start.
- `WidgetSummary` labels: local usage widgets use "Tokens" (the sum of the present token counts) and "Estimated cost"; metric panels use up to two readings labeled with the provider, dimension and kind, preferring the remaining percentage for subscription limits and the account-level billed cost for deployment cost; history uses the newest point of the first series; resource lists use "Resources" and "Healthy" counts.
- `UsageBreakdownRow.parser_state` combines the `device_parser_status` rows of the devices and tools behind a `DEVICE` or `TOOL` row with a fixed precedence, `PARTIAL` > `OK` > `NO_SOURCES` > `DISABLED`, implemented as an explicit comparison and not by iteration order, and sums `skipped_record_count`. The `PARTIAL_AGGREGATION` notice and the unspecified state of `MODEL` rows are unchanged.
- `Account.quotas` reports devices and connections per user, dashboards in the personal space and the largest widget count of a personal dashboard.
- `ListActivity` with an empty `space_id` returns the caller's device, enrollment, connection, collection-device, account and space-independent permission-denial events. With a space ID it returns dashboard, sharing and permission-denial events of that space. `ListDashboards` orders by `created_at`, then ID.
- `RevokeWidgetSharing` on a personal dashboard also sets `ENDED` with `OWNER_REVOKED`; `SetWidgetSharingScope` restores it to `PRIVATE`.

## Storage

PostgreSQL is the source of truth. Identifiers are UUID v7 unless they are Delcore IDs. Enum columns store the protocol's numeric values as `smallint`. Child rows of devices, connections, dashboards, widgets and price versions use foreign keys with cascading deletion, so the deletion job removes a parent and its data in one statement; `widget_sources` references connections and devices without a foreign key and is cleaned explicitly. Timestamps are `timestamptz`. Every user-owned row carries `user_id` and every lookup filters by it.

### Migrations and recovery

Migrations are SQL files under `servers/anydash-api/migrations/` with increasing numeric prefixes, applied only by the explicit `anydash-api migrate` command, never at startup. Follow the [service migration and recovery policy](repository-workflow-contract.md#service-migration-and-recovery): recover with a corrected forward release and, when state needs correction, a new forward migration. Never roll back to a previous image or binary and never write or apply down migrations.

### OCI packaging

One OCI image contains the `anydash-api` binary (API and worker), `servers/LICENSE`, `servers/NOTICE` and protocol license notices. Build it from the locked server workspace; never include environment files, Cargo targets or credentials in the build context. The unified release publishes it to GHCR through the [server image publication procedure](repository-workflow-contract.md#server-image-publication). Deployment and migration execution belong to private operator automation.

## Security

- Scope every lookup, cursor, request ID and lease to the authenticated user or device; return `NOT_FOUND` for entities of other users.
- External credentials never reach the server. Logs, metrics, audit events and error messages never contain secrets, tokens, device or user codes, prompts or response bodies.
- Store only SHA-256 digests of device codes, user codes and device tokens.
- Validate every enum, identifier, size and range before storage and reject violations with `INVALID_ARGUMENT`.
- The security review is ordinary code review. No separate threat model or penetration test is required.

## Logging

Use structured `tracing` logs in JSON (default) or text. Every request span carries the correlation ID, service, method, client kind and version, result category, `ErrorReason` and duration; device and connection IDs are allowed in logs but never in metric labels. Provider, status, tool and parser state labels use the lowercase enum value names without their prefix (for example `claude_code`, `rate_limited`, `partial`). Gauges backed by PostgreSQL are refreshed on each scrape and repeated by every replica. Operational logs are deleted 30 days after creation through external log collection.

Metrics (Prometheus, bounded labels): `anydash_api_requests_total{service,method,outcome}`, `anydash_api_timeouts_total` (requests that exceeded the 60-second request deadline and returned 504; it has no method label and is counted by the HTTP layer because the dropped handler cannot record them, and the 5xx alert and its request count include it), `anydash_gauge_refresh_failures_total` (scrapes that could not refresh the PostgreSQL-backed gauges; such a scrape still returns 200 with the last gauge values, so a database outage does not hide the request counters), `anydash_api_request_duration_seconds{service,method}`, `anydash_worker_job_runs_total{worker_job,outcome}`, `anydash_worker_job_last_success_timestamp_seconds{worker_job}` (not `job`, which is the Prometheus target label), `anydash_deletion_jobs_pending`, `anydash_deletion_oldest_pending_age_seconds`, `anydash_price_sync_last_success_timestamp_seconds`, `anydash_price_sync_validation_failures_total`, `anydash_collection_snapshots_total{provider,status}`, `anydash_parser_devices{tool,state}` (devices that uploaded in the last hour by latest parser state), `anydash_leases_active` and `anydash_lease_failovers_total{provider}`. Series with a known bounded label set (`anydash_worker_job_runs_total` for every worker job and outcome, and `anydash_collection_snapshots_total` for every provider and collection status except the unspecified values) are exposed at 0 from startup, so that Prometheus `increase()` sees the first failure.

Alerts (operator assets under `servers/anydash-api/ops/`, with rule tests). These are operational triggers, not SLOs:

- API 5xx rate above 2% for 5 minutes.
- A retention or deletion job fails, or a deletion job is still pending 20 hours after its request (24-hour deadline at risk).
- The LiteLLM price sync has not succeeded for 48 consecutive hours, or the price data fails validation.
- A provider's collection failure rate exceeds 20% in 1 hour (snapshots with status `FAILED` or `RATE_LIMITED`; `AUTH_EXPIRED` and `NOT_PROVIDED` are user or provider states, not failures).
- For Codex or Claude Code, 5% or more of the devices that uploaded in 1 hour report `PARTIAL`.

Runbooks cover startup and configuration, explicit migration, fix-forward recovery, Delcore and Logto outages, deletion backlog, price sync failure, provider endpoint changes (undocumented endpoints change without notice; the parser and provider alerts are the detection path; the response is a fix-forward collector release) and the minimum client version procedure.

## Build and Test

Run `cargo fmt --manifest-path servers/Cargo.toml --all --check`, `cargo clippy --locked --manifest-path servers/Cargo.toml --workspace --all-targets -- -D warnings`, `cargo test --locked --manifest-path servers/Cargo.toml` and the PostgreSQL tests with a disposable `TEST_DATABASE_URL` (`anydash_api_test` on port 55439 in CI). Mock Logto and Delcore, including `GetCurrentUser` pagination, `GetTenantStates` and `GetTenantMemberRoles`.

Required server integration tests on a disposable PostgreSQL database:

- Versioned upload idempotency (same version ignored, newer replaces, older ignored), corrections within 90 days and the 90-day retention cleanup.
- Lease epochs: concurrent acquisition grants one lease, 5-minute failover to the preferred device and otherwise the most recent heartbeat, rejection of an expired lease including after the old device returns, and concurrent heartbeats of devices holding crossed leases on shared connections.
- Hourly snapshot selection (last successful value in the hour) and late arrival by observation time; latest value changes only for a newer observation.
- The LiteLLM daily sync: new version only on change, failed fetch and invalid JSON keep the previous version and record the failure; price version selection by bucket time; "cannot be calculated" for missing prices and breakdowns; no recalculation after a new version.
- Quotas and rate limits, the minimum-version rejection before authentication, and 24-hour deletion completion for connections, devices, dashboards and account data.
- User withdrawal and tenant states `BLOCKED`, `DELETING` and `DELETED` through a mocked Delcore.
- Enrollment: code expiry, single use, 5-failure invalidation, refresh rotation, reuse detection and revocation, logout keeping the registration and re-login reattaching the device.

The PostgreSQL tests live in `servers/anydash-api/tests/` (`enrollment_usage.rs`, `leases_snapshots.rs`, `authorization.rs` and `lifecycle.rs`), each in its own schema with a loopback mock of Logto JWKS, the token endpoint, Delcore `GetCurrentUser` (one tenant per page), `GetTenantStates`, `GetTenantMemberRoles` and the LiteLLM JSON. Tests age rows with SQL instead of waiting for real time.

Required unit tests: 15-minute bucket aggregation into hourly and daily views for time zones with +5:30 and +5:45 offsets and across DST transitions; session counting in the start bucket; price version selection and the "cannot be calculated" path.

Required authorization tests: tenant isolation, the role matrix including Billing-only users, data-owner-only query and sharing changes, immediate revocation on unshare or leaving the team, team-space access without a collector device, and personal-space onboarding.

Load test gate: `servers/anydash-api/loadtest/` holds a repository-owned load test that simulates 1,000 concurrent active users and 5,000 collector devices with 1-minute heartbeats and local sync uploads and 5-minute external polling snapshots for 30 minutes. It must complete without errors against a production-like deployment. `anydash-load.mjs provision` connects operator-supplied test accounts and enrolls their devices within the enrollment rate limit, and exits non-zero when any request fails or any account, device, connection registration or dashboard widget is missing. `anydash-load.mjs run` drives the traffic and exits non-zero on any error. In its default capacity gate mode it refuses to start unless provisioning completed for at least 1,000 users and 5,000 devices and the run lasts at least 30 minutes; the explicit smoke mode drives a smaller completed population and never produces a gate result. See `servers/anydash-api/loadtest/README.md`. The maintainer records the result in the release validation record. Mocked and load tests do not replace real-account, real-device or store acceptance.
